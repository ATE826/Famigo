# Famigo API

Бэкенд Famigo: **Go + Gin + GORM + PostgreSQL**. Чат в реальном времени — WebSocket
([gorilla/websocket](https://github.com/gorilla/websocket)).

Запросы к базе пишутся через [GORM](https://gorm.io), а схему таблиц создают SQL-миграции
(`internal/database/migrations`). AutoMigrate из GORM для таблиц приложения не используется:
он не умеет триггеры (передача прав владельца), частичные уникальные индексы и CHECK-ограничения,
на которых держится целостность данных. Таблицы в виде Go-структур — в `internal/models`.

## Запуск

### Всё вместе одной командой (Docker)

Из корня репозитория:

```bash
docker compose --env-file .env --env-file secrets.env up --build
```

Откройте http://localhost:8080 — фронтенд, API (`/api`), база и Ollama поднимутся вместе.
Обычные настройки — в `.env` в корне, пароли и ключи — в `secrets.env` (см. «Настройки и секреты»).

Для локального запуска нужны Docker Compose 2.30+ и NVIDIA GPU; на Windows — Docker Desktop
с WSL 2 и драйвером NVIDIA. При первом старте сервис `ollama-init` скачает `AI_MODEL`
(по умолчанию `gemma4:e4b`) параллельно с запуском сайта. Бэкенд ждёт только готовности базы,
фронтенд — готовности бэкенда. До завершения загрузки модели подбор блюд недоступен.
Загрузка занимает время и место на диске:
локальная модель из Windows автоматически не копируется. Модели сохраняются в томе
`famigo-ollama`; обычный `docker compose down` их не удаляет.

Для разработки без файла секретов: `docker compose up -d --build`.
Проверить загрузку: `docker compose logs -f ollama-init`.
Проверить модель: `docker compose exec ollama ollama list`.
Посмотреть использование GPU после запроса: `docker compose exec ollama ollama ps`.
Скачивание подготавливает модель на диске, в память она загружается при первом запросе.

### Только бэкенд (без Docker)

Нужны Go 1.27+ и PostgreSQL 15+.

```bash
cp ../secrets.env.example ../secrets.env    # и впишите JWT_SECRET и DATABASE_URL
go run ./cmd/api
```

Проверка: http://localhost:8080/api/health → `{"status":"ok","database":"ok"}`.
Миграции из `internal/database/migrations` применяются сами при запуске.

## Настройки и секреты

Настройки разделены на два файла:

| Файл | Что внутри | В git |
|---|---|---|
| `.env` (в корне — для Docker, в `backend/` — без Docker) | обычные настройки: режим, адреса, лимиты | да |
| `secrets.env` (в корне) | `JWT_SECRET`, `MESSAGE_KEYS`, `POSTGRES_PASSWORD`, `DATABASE_URL`, `AI_API_KEY` (для облачной нейросети) | **нет** (`.gitignore`) |
| `secrets.env.example` | образец без настоящих значений | да |

Что важнее, если одна настройка задана в нескольких местах: переменная окружения → `.env` → `secrets.env`.

**Вынести `secrets.env` из проекта** (например, в `C:\secrets\famigo\secrets.env`) можно, ничего не ломая:

- Docker: `docker compose --env-file .env --env-file C:\secrets\famigo\secrets.env up --build`
- Без Docker: задайте путь в переменной `SECRETS_FILE` (в `backend/.env` или в системе).
  Если путь указан, а файла нет, сервер не запустится и скажет об этом, а не подставит временный секрет.

Без `SECRETS_FILE` сервер ищет `secrets.env` в текущей папке и на уровень выше.

**Заменить секреты** (если они попали в чат, мессенджер, git или вы просто хотите сменить их) — скрипт
`scripts/rotate-secrets.ps1`. Он создаёт новые случайные `JWT_SECRET` и пароль базы, переписывает ваш
`secrets.env` и **ничего не выводит на экран**. С ключом `-ApplyToDocker` он также меняет пароль в
запущенной Docker-базе (данные сохраняются) и перезапускает контейнеры:

```powershell
powershell -ExecutionPolicy Bypass -File scripts\rotate-secrets.ps1 -SecretsFile C:\secrets\famigo\secrets.env -ApplyToDocker
```

После замены пользователи один раз входят заново. Без `-ApplyToDocker` Docker не трогается: тогда
пароль базы в контейнере останется прежним, пока вы не пересоздадите базу (`docker compose down -v`,
**это сотрёт данные**).

## Структура

```text
cmd/api/main.go              точка входа: настройки → база → миграции → сервер
internal/
  config/                    настройки из окружения, .env и secrets.env
  database/                  подключение GORM, ошибки базы, миграции (migrations/*.sql)
  models/                    таблицы базы в виде структур GORM
  httpx/                     ошибки, чтение и проверка запросов, middleware, ограничение частоты
  server/                    gin, общие middleware, все маршруты (routes.go)
  auth/                      регистрация, вход, JWT, refresh-токены, пароли
  users/                     профиль, аватар, предпочтения в еде, настройки, удаление аккаунта
  families/                  семья, участники, роли, приглашения, проверка членства
  homes/  products/          дома, дела по дому, холодильник
  budget/ calendar/          доходы и расходы, события
  chats/  notifications/     чаты (REST + WebSocket), уведомления
  subscriptions/             тарифы и подписка семьи
  recipes/  ai/              блюда от нейросети из продуктов холодильника; клиент OpenAI-совместимого API
  locations/ safety/ gallery/ receipts/   заготовки разделов после MVP
```

В каждом разделе: `handler.go` (HTTP) → `service.go` (правила и права) → `repository.go` (запросы GORM).

## API

Все ответы — JSON. Ошибка всегда одного вида:
`{"error": {"code": "not_found", "message": "Дом не найден", "fields": {...}}}`.
Защищённые адреса требуют заголовок `Authorization: Bearer <accessToken>`.
Суммы — в **копейках**, даты — `2026-10-27`, время — RFC 3339.

| Метод и адрес | Что делает |
|---|---|
| `POST /api/auth/register` | регистрация (имя, почта, пароль, дата рождения, два согласия) |
| `POST /api/auth/login` | вход → `accessToken` + кука с refresh-токеном |
| `POST /api/auth/refresh` | новый `accessToken` по куке |
| `POST /api/auth/logout`, `/logout-all` | выйти здесь / на всех устройствах |
| `GET/PATCH/DELETE /api/me` | профиль; удаление аккаунта — с паролем |
| `PUT /api/me/password`, `/me/food`, `/me/settings` | пароль, предпочтения в еде (нужно согласие), настройки |
| `PUT/DELETE /api/me/avatar` | загрузить (multipart, поле `avatar`) / удалить аватар |
| `GET /api/notifications`, `POST .../:id/read`, `POST .../read-all` | уведомления |
| `GET/POST /api/families`, `POST /api/families/join` | мои семьи, создать, вступить по коду |
| `GET/PATCH /api/families/:id` | семья с участниками, переименовать |
| `POST /api/families/:id/invite` | код приглашения на 12 часов |
| `PATCH/DELETE /api/families/:id/members/:userId`, `PUT .../home` | роль, удалить, поселить в дом |
| `POST /api/families/:id/leave`, `/owner` | выйти из семьи, передать права владельца |
| `.../subscription` (+ `/cancel`, `/resume`) | тариф семьи (оплата пока демо) |
| `.../homes`, `.../homes/:homeId`, `.../tasks` | дома и дела по дому |
| `.../homes/:homeId/products` | холодильник |
| `POST .../homes/:homeId/recipes/suggest` | пять блюд от нейросети (Premium+): `{"servings": 3, "allMembers": false, "memberIds": [...], "language": "ru", "category": "soup"}` |
| `.../transactions`, `.../budget/summary?month=2026-10` | бюджет |
| `.../events?from=…&to=…` | календарь |
| `.../chats`, `.../chats/direct`, `.../chats/:chatId/messages`, `.../read` | чаты |
| `POST /api/chats/ws-ticket`, `GET /api/chats/ws?ticket=…` | одноразовый билет и подключение WebSocket |

`...` = `/api/families/:familyId`.

### WebSocket чата

Браузер не умеет добавлять `Authorization` к WebSocket, а токен в адресе попал бы в логи.
Поэтому фронтенд сначала берёт одноразовый билет на 30 секунд (`POST /api/chats/ws-ticket`)
и с ним подключается к `/api/chats/ws?ticket=…`.

- От сервера: `{"type":"message", "familyId", "chatId", "clientId", "message"}`,
  `{"type":"read", "chatId", "userId", "at"}`, `{"type":"deleted", "chatId", "messageId"}`,
  `{"type":"error", "clientId", "code", "message"}`.
- От клиента: `{"type":"send", "familyId", "chatId", "text", "clientId"}`,
  `{"type":"read", "familyId", "chatId"}`.

Соединение живёт не дольше 15 минут (как access-токен), потом сервер закрывает его,
и фронтенд переподключается с новым билетом.

## Безопасность

- **SQL-инъекции.** Значения передаются только параметрами GORM (`Where("email = ?", email)`),
  SQL никогда не склеивается со строками от пользователя. В `Where`/`Order`/`Select` — только
  строки-константы из кода. Тело запроса не декодируется прямо в модель GORM.
- **Чужие данные (IDOR).** Все семейные адреса проходят через `RequireMember`, каждый запрос
  к базе фильтруется по `family_id`. На чужое — `404`, а не `403`: не видно, что запись существует.
- **Пароли.** bcrypt (cost 12), длина 8–72 байта. Вход отвечает одинаково для «нет почты» и
  «неверный пароль» и тратит одинаковое время.
- **Токены.** Access JWT на 15 минут (только HS256, проверяются издатель, аудитория, срок).
  В токене есть номер сессии (`sid`), и сервер на каждый запрос проверяет в базе, что сессия не завершена:
  выход, смена пароля, «выйти везде» и удаление аккаунта действуют **сразу**, а не через 15 минут.
  Открытое соединение WebSocket тоже закрывается после завершения сессии (проверка раз в 20 секунд).
  Refresh — случайные 256 бит в httpOnly-куке `SameSite=Strict`, в базе — только хеш, ротация
  при каждом использовании. Повтор старого токена в течение 30 секунд после обмена разрешён
  (перезагрузка страницы, несколько вкладок), позже — считается кражей и завершает все сессии.
  Проверка текущего пароля (смена пароля, удаление аккаунта) — не чаще 10 раз в минуту.
- **CSRF.** Кука входа видна только `/api/auth` и не уходит с чужих сайтов; дополнительно
  проверяется заголовок `Origin`.
- **Подмена полей.** Неизвестные поля в JSON — ошибка 400 (нельзя прислать `"role": "owner"`).
- **Ограничение частоты.** Общее по IP (для IPv6 — по сети /64), отдельное на вход/регистрацию
  (регистрация вчетверо строже: ответ «почта уже занята» нельзя использовать для быстрого перебора чужих почт),
  на одну почту, на коды приглашения, сообщения, команды и билеты WebSocket, загрузки.
- **WebSocket.** Одноразовые билеты, проверка `Origin` (защита от CSWSH), до 10 подключений
  на человека, лимит размера сообщения, медленный клиент отключается, события получают
  только участники чата.
- **Загрузка аватара.** До 5 МБ, тип по содержимому (JPEG/PNG/GIF/WebP, без SVG), проверка
  разрешения до распаковки, перекодирование в новый JPEG (без EXIF и «прицепленного» кода),
  случайное имя файла.
- **Заголовки.** `nosniff`, запрет фреймов, CSP, `no-store`, `Cross-Origin-Resource-Policy`, HSTS в production.
- **Логи.** Журнал GORM пишет запросы без значений: почта, хеши и сообщения в лог не попадают.
- **Шифрование сообщений в базе.** Текст сообщений хранится зашифрованным (AES-256-GCM, пакет
  `internal/fieldcrypt`): дамп базы или резервная копия без ключа не раскрывают переписку. Подробнее ниже.
- **Ошибки.** Наружу — только код и текст для человека; подробности — в лог с `request_id`.
- **Docker.** Сервер не от root в минимальном образе, база не открыта наружу,
  nginx перезаписывает `X-Forwarded-For`.

## Шифрование сообщений в базе

Ключ задаётся в `secrets.env`: `MESSAGE_KEYS=1:<ключ в base64>` (`openssl rand -base64 32`, перед ним «1:»).
В `production` без него сервер не запустится. В разработке без ключа сообщения хранятся открытым
текстом, и сервер пишет об этом предупреждение.

Как это устроено:
- В колонке `messages.text` лежит строка `enc:v1:<номер ключа>:<nonce и шифртекст>`.
- Шифрование на границе «сервис ↔ база» (`internal/chats`): API и WebSocket отдают уже расшифрованный текст,
  фронтенд ничего не знает о шифровании.
- Шифртекст привязан к чату и номеру сообщения (AAD): перенести его в другое сообщение нельзя, он не расшифруется.
  Подмену данных GCM тоже обнаруживает.
- **Старые сообщения** (открытым текстом) шифруются при запуске сервера, пачками по 500.
- **Смена ключа:** допишите новый ПЕРЕД старым (`MESSAGE_KEYS=2:новый,1:старый`) и перезапустите сервер:
  он перешифрует все сообщения. Старый ключ удаляйте только после этого. Если запись зашифрована ключом,
  которого нет в списке, в чате будет «[сообщение не удалось расшифровать]», а в логе ошибка.
- Случайный nonce безопасен примерно до 4 миллиардов сообщений на один ключ: на таком объёме меняйте ключ.

**Потеряете ключ — сообщения не прочитать.** Храните копию отдельно (менеджер паролей).

Чего это не даёт: это **не сквозное шифрование**. Сервер знает ключ и видит текст, поэтому взлом самого
сервера (или кража ключа вместе с базой) раскрывает переписку. Длина сообщения видна по длине шифртекста.
Защита именно от утечки базы и резервных копий.

## Подбор блюд нейросетью

Нейросеть придумывает блюда из продуктов холодильника дома с учётом аллергий, непереносимостей и диет
тех, кто будет есть (`memberIds`, по умолчанию вся семья), и отмечает, что есть в холодильнике, а что докупить.
`allMembers=true` учитывает всю семью. При `allMembers=false` применяются ограничения только из `memberIds`;
пустой список означает отсутствие ограничений. Без флага сохраняется прежнее поведение: пустой список — вся семья.
Один общий выбор на странице применяется и к AI-подборке, и к готовым рецептам.
Модель сначала выбирает разные идеи, затем отдельным запросом подробно расписывает каждую.
Рецепт содержит обязательные этапы подготовки, приготовления и подачи: не менее шести подробных шагов
для блюда и четырёх для напитка, с продуктами каждого шага. Сервер объединяет их с общим составом:
ингредиенты подачи и соусов тоже попадают в теги и покупки. Дополнительный запрос к модели сверяет
состав с текстом всех шагов и добавляет пропущенные продукты до проверки ограничений. Базовые продукты (`staple`) видны в составе,
но считаются уже имеющимися дома. Пометки о покупках в шагах не принимаются.
Перед запросом из списка для модели исключаются продукты, которые не проходят выбранные ограничения.
Сами продукты в холодильнике не изменяются. Модель получает также подсказки о запрещённых группах,
а готовые рецепты повторно проверяются сервером, включая инструкции по приготовлению.
Успешный ответ содержит ровно пять разных проверенных рецептов. `category`: `any` (по умолчанию),
`snack`, `hot`, `cold`, `soup`, `salad`, `bakery`, `dessert`, `drink`.
Категория передаётся модели вместе с пояснением, блюда должны различаться составом или приготовлением.
Сервер исключает совпадающие названия и рецепты с одновременно одинаковыми составом и инструкциями.
Один набор продуктов может использоваться в разных блюдах, а общие шаги допустимы для разных составов
(например, фруктовых смузи). По отдельности эти совпадения не считаются повтором. Если рецептов не хватает,
он запрашивает недостающие (до трёх попыток генерации со сверкой состава в пределах общего `AI_TIMEOUT`).
Ограничения в питании не ослабляются ради количества: если подборка не заполнена,
API возвращает `ai_incomplete`, а интерфейс предлагает повторить запрос или сменить категорию.
Доступно на тарифе Premium+.

**Провайдер меняется настройками, без правок кода** — подходит любой OpenAI-совместимый API:

| Где модель | `AI_BASE_URL` | `AI_MODEL` | `AI_API_KEY` (в `secrets.env`) |
|---|---|---|---|
| Ollama вместе с Famigo в Docker (по умолчанию) | `http://ollama:11434/v1` | `gemma4:e4b` | не нужен |
| Ollama на компьютере, бэкенд без Docker | `http://localhost:11434/v1` | `gemma4:e4b` | не нужен |
| Ollama на компьютере, бэкенд в Docker | `http://host.docker.internal:11434/v1` | `gemma4:e4b` | не нужен |
| Облако (Gemini, OpenRouter, Groq…) | `https://…` адрес провайдера | модель провайдера | нужен |

Остальное: `AI_REASONING=none` (без «размышлений», быстрее), `AI_JSON_MODE=schema|object`,
`AI_TIMEOUT=5m`, `AI_MAX_CONCURRENT=1`. Пустой `AI_BASE_URL` — подбор выключен, API отвечает 503.

В конфигурации Compose Ollama доступна по внутреннему адресу `ollama:11434`: порт наружу
не публикуется, запускать Ollama в Windows отдельно не требуется. Контейнер держит модель
в памяти 30 минут после запроса. По умолчанию используется меньшая модель E4B.
Если видеопамяти не хватает, Ollama может использовать оперативную память и CPU;
Docker должен иметь достаточно памяти для загрузки выбранной модели.
Для запуска бэкенда без Docker Ollama по-прежнему запускается отдельно на компьютере.
Таблица выше описывает адреса API; стандартный Compose рассчитан на локальную Ollama
и запускает `ollama-init` с моделью из `AI_MODEL` параллельно с бэкендом.
Загрузчик сначала проверяет наличие модели и скачивает её только при отсутствии.
Для обновления уже установленной модели: `docker compose exec ollama ollama pull gemma4:e4b`.

Если API сообщает, что нейросеть недоступна, проверьте `docker compose logs backend`.
Ошибка `model '…' not found` означает, что выбранная модель ещё не установлена в Docker.
Запустите `docker compose up -d` и для подбора блюд дождитесь успешного завершения `ollama-init`:
`docker compose logs -f ollama-init`. После смены `AI_MODEL` также выполняйте `up -d`,
чтобы Compose применил новые настройки к бэкенду и загрузчику модели.

Защита:
- **Модели уходят только продукты и ограничения** — без имён, почты и других личных данных.
  Испорченные продукты не отправляются.
- **Ответу нейросети не верим.** Он разбирается строго по JSON-схеме, строки чистятся и обрезаются, а каждое
  блюдо сверяется с ограничениями по словам в названии, ингредиентах и шагах (`recipes/matcher.go`). Блюдо с нарушением отбрасывается
  (в ответе `dropped`). Диеты без явного списка продуктов (кето, сыроедение) проверяет только модель,
  поэтому на странице есть предупреждение «проверяйте состав».
- **Prompt injection.** Названия продуктов и пункты профиля уходят модели отдельным сообщением в виде JSON,
  а инструкция велит считать их данными. Даже если модель поддастся, она умеет только вернуть текст.
- **Лимиты.** 20 запросов в час на человека (не больше 5 подряд), к локальной модели — по одному запросу
  за раз и очередь до 4; остальным — «модель занята» (503).
- Ключ облачного провайдера лежит только на сервере; по `http://` к чужому адресу сервер его не отправит.
