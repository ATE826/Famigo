# Famigo API

Бэкенд Famigo: **Go + Gin + GORM + PostgreSQL**. Чат в реальном времени — WebSocket
([gorilla/websocket](https://github.com/gorilla/websocket)).

Документация обновлена **26.11.2026**; чаты, медиа и новые миграции сверены с кодом. Текущие внешние интеграции: Яндекс SMTP,
GigaChat и Yandex SmartCaptcha. Подробности общего интерфейса — в [README проекта](../README.md).

Запросы к базе пишутся через [GORM](https://gorm.io), а схему таблиц создают SQL-миграции
(`internal/database/migrations`). AutoMigrate из GORM для таблиц приложения не используется:
он не умеет триггеры (передача прав владельца), частичные уникальные индексы и CHECK-ограничения,
на которых держится целостность данных. Таблицы в виде Go-структур — в `internal/models`.

## Запуск

### Всё вместе одной командой (Docker)

Из корня репозитория:

```bash
docker compose --env-file .env --env-file secrets.env up --build
```

Обычные настройки — в `.env` в корне, пароли и ключи — в `secrets.env` (см. «Настройки и секреты»).

Откройте http://localhost:8080/. Backend ждёт готовности PostgreSQL, frontend — backend. Генерация использует внешний GigaChat API; локальная модель и GPU не требуются.

### Только бэкенд (без Docker)

Нужны Go по `go.mod` (`go 1.27.1`, toolchain `go1.27.3`) и PostgreSQL. В Compose используется PostgreSQL 17.

```bash
cd backend
# Создайте ../secrets.env по примеру в корневом README; задайте DATABASE_URL, JWT_SECRET и SMTP_PASSWORD.
go run ./cmd/api
```

Проверка: http://localhost:8080/api/health → `{"status":"ok","database":"ok"}`.
Миграции из `internal/database/migrations` применяются сами при запуске.

## Настройки и секреты

Настройки разделены на два файла:

| Файл | Что внутри | В git |
|---|---|---|
| `.env` (в корне — для Docker, в `backend/` — без Docker) | обычные настройки: режим, адреса, лимиты | да |
| `secrets.env` (в корне) | Пароли БД и SMTP, `JWT_SECRET`, `MESSAGE_KEYS`, `DATABASE_URL`, `DOCKER_DATABASE_URL`, `GIGACHAT_AUTH_KEY`, ключи SmartCaptcha; `AI_API_KEY`/`RESEND_API_KEY` при выборе альтернативных провайдеров | **нет** (`.gitignore`) |

Что важнее, если одна настройка задана в нескольких местах: переменная окружения → `.env` → `secrets.env`.

**Внешний файл секретов**, например `C:\secrets\famigo\secrets.env`, настраивается по-разному для Go и Docker:

- Docker: передайте файл через `--env-file` для подстановок Compose и измените `backend.env_file.path` в Compose на фактический путь. Одного `--env-file` недостаточно для `SMTP_PASSWORD`, `GIGACHAT_AUTH_KEY` и ключей SmartCaptcha: в текущем Compose он передаётся через `env_file`, указывающий на корневой `./secrets.env`.
- Без Docker: задайте путь в переменной `SECRETS_FILE` (в `backend/.env` или в системе).
  Если путь указан, а файла нет, сервер не запустится и скажет об этом, а не подставит временный секрет.

Без `SECRETS_FILE` сервер ищет `secrets.env` в текущей папке и на уровень выше.

**Смена пароля БД.** Инструкция находится в [корневом README](../README.md#подключение-к-бд-через-pgadmin). Сначала меняется пароль роли PostgreSQL, затем значения в файле и окружение контейнеров. Для новой установки используйте `secrets.env.example` и [инструкцию заполнения](../README.md#подготовка). Скрипта `scripts/rotate-secrets.ps1` в текущей ветке нет; автоматическая ротация им не поддерживается. Удалять том БД для смены пароля не нужно.

Внешний pgAdmin подключается к `127.0.0.1:15432`, backend в Docker — к `db:5432`. `DOCKER_DATABASE_URL` задаёт внутреннюю строку подключения, а `DATABASE_URL` в файле используется для локального Go-процесса. В URL пароль кодируется, в `POSTGRES_PASSWORD` записывается исходным. Изменение `JWT_SECRET` инвалидирует JWT и HMAC-коды; ключи `MESSAGE_KEYS` меняются отдельно с сохранением старых ключей до перешифрования.

## Тесты

Тесты без отдельной БД проверяют в том числе формат ответа SmartCaptcha и
хосты с портами. С `FAMIGO_TEST_DATABASE_URL` также запускаются `TestCaptchaAuthFlow`
и `TestPasswordResetFlow` в `internal/auth`: обязательная капча регистрации,
сохранение требования после ошибки входа, повтор токена, сбой провайдера и
подтверждение кодом. Эти сценарии используют поддельные CAPTCHA/почту, не решают
настоящие задания и не отправляют реальные письма.

```bash
go test ./...
```

Интеграционный тест (настоящий HTTP + настоящая база, включая попытки атак) запускается,
если указать **пустую** тестовую базу:

```powershell
$env:FAMIGO_TEST_DATABASE_URL = 'postgres://famigo:<URL-кодированный пароль>@localhost:15432/famigo_test?sslmode=disable'
go test ./internal/server ./internal/auth -v
Remove-Item Env:FAMIGO_TEST_DATABASE_URL
```

Проверки чатов включают:

- несколько печатающих участников и несколько соединений одного пользователя;
- запрет удаления чужого сообщения для `scope=me` и `scope=all` без изменения данных;
- повторное личное скрытие своего сообщения и сохранность общих вложений;
- очистку вложений при удалении у всех и доступность пересланной копии;
- альбом из нескольких файлов с общей подписью и ссылкой-ответом;
- шифрование файлов альбома, новые ID при пересылке и сохранность копии;
- отказ от всего альбома при неверном файле, лимит 10 файлов и подпись одиночного фото;
- метаданные голосового и отклонение заявленной длительности кружочка более минуты.

Интеграционные проверки изменяют данные и применяют миграции: рабочую БД
и её `DATABASE_URL` в `FAMIGO_TEST_DATABASE_URL` не используйте.

## API

### Семейная подписка и права управления

В `subscriptions` одна запись на `family_id`. Тариф и его возможности общие для
всех участников этой семьи; `payer_id` — пользователь, оформивший подписку, а не
отдельный источник прав. `GET /api/families/:familyId/subscription` доступен всем
участникам. Создание/смена тарифа (`POST .../subscription`), отмена и возобновление
настройки продления (`POST .../subscription/cancel`, `.../resume`) разрешены только
текущим ролям `owner` и `admin`. Бывший плательщик с ролью `member` получает 403.
Проверка выполняется в сервисе, поэтому скрытие кнопок не является единственной защитой.

Семейные цены с 21.11.2026: Premium — 499 ₽/месяц или 4 990 ₽/год;
Premium+ — 1 499 ₽/месяц или 14 990 ₽/год. API передаёт цены в копейках
(`49900/499000`, `149900/1499000`). Изменение цен не меняет существующий срок
подписки, роль или плательщика; платежей, перерасчётов и списаний по-прежнему нет.
Реальное оформление недоступно при `DEMO_PAYMENTS=false`.

Расходы, выручка, прибыль и годовые сценарии обоих тарифов описаны в
[финансовой модели](../_docs/economics.md). Цены не являются серверными квотами:
месячный AI-бюджет и общая квота вложений чатов пока не реализованы.

### Формат и маршруты

Ответы с данными — JSON; загрузка аватаров использует multipart, выдача изображений — двоичные данные, а некоторые успешные операции возвращают 204 без тела. Ошибки API имеют вид:
`{"error": {"code": "not_found", "message": "Дом не найден", "fields": {...}}}`.
Защищённые адреса требуют заголовок `Authorization: Bearer <accessToken>`.
Суммы — в **копейках**, даты — `2026-10-27`, время — RFC 3339.

| Метод и адрес | Что делает |
|---|---|
| `GET /api/auth/captcha` | публичные настройки SmartCaptcha и требование проверки после ошибки входа |
| `POST /api/auth/register` | временная заявка регистрации → `challengeId`; аккаунт создаётся после проверки кода |
| `POST /api/auth/login` | проверка пароля и отправка кода → `challengeId`, без сессии |
| `POST /api/auth/email/verify`, `/api/auth/email/resend` | проверка кода → `accessToken` и refresh-cookie; повторная отправка |
| `POST /api/auth/password/request`, `/api/auth/password/verify`, `/api/auth/password/reset` | запрос кода, проверка и установка нового пароля |
| `POST /api/auth/refresh` | новый `accessToken` по куке |
| `POST /api/auth/logout`, `/logout-all` | выйти здесь / на всех устройствах |
| `GET/PATCH/DELETE /api/me` | профиль; удаление аккаунта — с паролем |
| `PUT /api/me/password`, `/me/food`, `/me/settings` | пароль, предпочтения в еде (без повторного чекбокса), настройки |
| `PUT/DELETE /api/me/avatar` | загрузить (multipart, поле `avatar`) / удалить аватар |
| `GET/POST /api/me/recipes`, `DELETE /api/me/recipes/:favoriteID` | личные избранные рецепты; проверка владельца записи |
| `GET /api/notifications`, `POST .../:id/read`, `POST .../read-all` | уведомления |
| `GET/POST /api/families`, `POST /api/families/join` | мои семьи, создать, вступить по коду |
| `GET/PATCH /api/families/:id` | семья с участниками, переименовать |
| `POST /api/families/:id/invite` | код приглашения на 12 часов |
| `PATCH/DELETE /api/families/:id/members/:userId`, `PUT .../home` | роль, удалить, поселить в дом |
| `POST /api/families/:id/leave`, `/owner` | выйти из семьи, передать права владельца |
| `.../subscription` (+ `/cancel`, `/resume`) | тариф семьи (оплата пока демо) |
| `.../homes`, `.../homes/:homeId`, `.../tasks` | дома и дела по дому |
| `.../homes/:homeId/products` | холодильник |
| `POST .../homes/:homeId/recipes/suggest` | пять блюд от нейросети (Premium+): `{"servings": 3, "allMembers": false, "memberIds": [...], "language": "ru", "category": "soup"}` |
| `.../transactions`, `.../budget/summary?month=2026-10` | бюджет |

### WebSocket чата

Браузер не умеет добавлять `Authorization` к WebSocket, а токен в адресе попал бы в логи.
Поэтому фронтенд сначала берёт одноразовый билет на 30 секунд (`POST /api/chats/ws-ticket`)
и с ним подключается к `/api/chats/ws?ticket=…`.

| Направление | `type` | Основные поля и смысл |
| --- | --- | --- |
| Клиент → сервер | `send` | `familyId`, `chatId`, `text`, `clientId`: текстовое сообщение |
| Клиент → сервер | `read` | `familyId`, `chatId`, `messageIds`: просмотр конкретных сообщений |
| Клиент → сервер | `typing` | `familyId`, `chatId`, `typing`: `true` при наборе, `false` при завершении |
| Сервер → клиент | `message` | `familyId`, `chatId`, `clientId`, `message`: новое сообщение, включая rich-содержимое |
| Сервер → клиент | `read` | `familyId`, `chatId`, `userId`, `at`, `allReadIds`, `unread`: новые просмотры и счётчики |
| Сервер → клиент | `deleted` | `familyId`, `chatId`, `messageId`: собственное сообщение удалено автором для всех |
| Сервер → свои подключения | `hidden` | `familyId`, `chatId`, `messageId`: автор скрыл своё сообщение только у себя |
| Сервер → клиент | `typing` | `familyId`, `chatId`, `userIds`: снимок набирающих участников без текста сообщений |
| Сервер → клиент | `error` | `clientId`, `code`, `message`: ошибка команды |

Удаление и загрузка вложений выполняются через REST; события WebSocket
синхронизируют изменения с клиентами. Выбор нескольких сообщений и просмотр
со стрелками — клиентские сценарии, отдельного bulk-delete или bulk-forward API нет.
Пересылка/удаление выбранного набора идут отдельными запросами по сообщениям;
альбом при этом остаётся одним сообщением. Несколько запросов не образуют общей
транзакции: при ошибке ранее подтверждённые операции уже выполнены.

Просмотры привязаны к конкретным сообщениям в таблице `message_views`.
`POST /api/families/:familyId/chats/:chatId/read` принимает JSON
`{"messageIds":["UUID"]}` (от 1 до 100 ID) и возвращает такое же событие `read`.
Экран отправляет ID только появившихся в видимой области сообщений в активной вкладке.
Открытие чата и отправка ответа сами по себе не отмечают историю прочитанной.
Поле сообщения `readByAll` и массив события `allReadIds` означают, что сообщение
увидели все текущие участники чата, кроме автора. Пропущенные сообщения остаются
непрочитанными; повторная отправка отметки идемпотентна. Статусы интерфейса
«Доставлено» (одна галочка) и «Прочитано» (две галочки) переведены на шесть языков.

Соединение живёт не дольше 15 минут (как access-токен), потом сервер закрывает его,
и фронтенд переподключается с новым билетом.

## Безопасность

- **SQL-инъекции.** Значения передаются только параметрами GORM (`Where("email = ?", email)`),
  SQL никогда не склеивается со строками от пользователя. В `Where`/`Order`/`Select` — только
  строки-константы из кода. Тело запроса не декодируется прямо в модель GORM.
- **Чужие данные (IDOR).** Все семейные адреса проходят через `RequireMember`, каждый запрос
  к базе фильтруется по `family_id`. На чужое — `404`, а не `403`: не видно, что запись существует.
- **Пароли.** bcrypt (cost 12), минимум 8 символов, максимум 72 байта. При регистрации обязательны латинская буква, цифра и специальный символ; пробел не заменяет знак. Вход отвечает одинаково для «нет почты» и
  «неверный пароль» и тратит одинаковое время.
- **Токены.** Access JWT на 15 минут (только HS256, проверяются издатель, аудитория, срок).
  В токене есть номер сессии (`sid`), и сервер на каждый запрос проверяет в базе, что сессия не завершена:
  выход, смена пароля, «выйти везде» и удаление аккаунта действуют **сразу**, а не через 15 минут.
  Открытое соединение WebSocket тоже закрывается после завершения сессии (проверка раз в 20 секунд).
  Refresh — случайные 256 бит в httpOnly-куке `SameSite=Strict`, в базе — только хеш, ротация
  при каждом использовании. Повтор старого токена в течение 30 секунд после обмена разрешён
  (перезагрузка страницы, несколько вкладок), позже — считается кражей и завершает все сессии.
  Проверка текущего пароля (смена пароля, удаление аккаунта) — не чаще 10 раз в минуту.
- **CSRF.** Кука входа видна только `/api/auth` и не уходит с чужих сайтов; дополнительно
  проверяется заголовок `Origin`.
- **Подмена полей.** Неизвестные поля в JSON — ошибка 400 (нельзя прислать `"role": "owner"`).
- **Ограничение частоты.** Общее по IP (для IPv6 — по сети /64), отдельное на вход/регистрацию
  (регистрация вчетверо строже: ответ «почта уже занята» нельзя использовать для быстрого перебора чужих почт),
  на одну почту, на коды приглашения, сообщения, команды и билеты WebSocket, загрузки.
- **SmartCaptcha.** При настроенных ключах обязательна для регистрации и после неверной попытки входа. Требование хранится в БД по HMAC IP, токен проверяется на сервере один раз, хост с портом нормализуется перед сравнением. Ошибки сервиса не отключают защиту.
- **WebSocket.** Одноразовые билеты, проверка `Origin` (защита от CSWSH), до 10 подключений
  на человека, лимит размера сообщения, медленный клиент отключается, события получают
  только участники чата.
- **Загрузка аватара.** До 5 МБ, тип по содержимому (JPEG/PNG/GIF/WebP, без SVG), проверка
  разрешения до распаковки, перекодирование в новый JPEG (без EXIF и «прицепленного» кода),
  случайное имя файла.
- **Заголовки.** `nosniff`, запрет фреймов, CSP, `no-store`, `Cross-Origin-Resource-Policy`, HSTS в production.
- **Логи.** Журнал GORM пишет запросы без значений: почта, хеши и сообщения в лог не попадают.
- **Шифрование содержимого чатов.** При заданном `MESSAGE_KEYS` AES-256-GCM защищает `messages.text`, `messages.details` и содержимое `chat_media`, включая имена файлов и MIME-типы. Подробнее ниже.
- **Ошибки.** Наружу — только код и текст для человека; подробности — в лог с `request_id`.
- **Docker.** Сервер не от root в минимальном образе, порт базы опубликован только на `127.0.0.1:15432`,
  nginx перезаписывает `X-Forwarded-For`.

## Шифрование сообщений в базе

Ключ задаётся в `secrets.env`: `MESSAGE_KEYS=1:<ключ в base64>` (`openssl rand -base64 32`, перед ним «1:»).
В `production` без него сервер не запустится. В разработке без ключа сообщения хранятся открытым
текстом, и сервер пишет об этом предупреждение.

Как это устроено:
- В колонке `messages.text` лежит строка `enc:v1:<номер ключа>:<nonce и шифртекст>`.
- В JSONB `messages.details` хранится JSON-строка с зашифрованным содержимым; пустой объект `{}` не шифруется. API возвращает обычный JSON-объект.
- `chat_media.data` хранит бинарный конверт `enc:bin:v1:<номер ключа>:` с nonce и шифртекстом без раздувания файла в Base64. Имя и MIME шифруются отдельно. AAD включает чат, сообщение, ID вложения и имя поля. При пересылке файл расшифровывается после проверки доступа к источнику и шифруется для нового места. Повреждённое вложение не выдаётся.
- Идентификаторы, авторы, даты, размеры, членство и отметки просмотра не скрываются. Рецепты в личном избранном вне чатов не входят в этот механизм.
- Шифрование на границе «сервис ↔ база» (`internal/chats`): API и WebSocket отдают уже расшифрованный текст,
  фронтенд ничего не знает о шифровании.
- Шифртекст привязан к чату и номеру сообщения (AAD): перенести его в другое сообщение нельзя, он не расшифруется.
  Подмену данных GCM тоже обнаруживает.
- **Старые записи** переводятся при запуске: текст и детали пачками по 100, вложения по одному, чтобы не загружать множество видео в память. При неизвестном ключе или повреждении записи запуск прекращается: нужно восстановить ключ/данные. Удалённые сообщения с сохранившимися историческими деталями и файлами также обрабатываются.
- **Смена ключа:** допишите новый ПЕРЕД старым (`MESSAGE_KEYS=2:новый,1:старый`) и перезапустите сервер:
  он перешифрует содержимое чатов. Старые ключи сохраняйте для восстановления исторических резервных копий. Не удаляйте их до успешного перевода всех записей и проверки восстановления.
- Случайный nonce безопасен примерно до 4 миллиардов операций шифрования на один ключ: на таком объёме меняйте ключ.

**Потеряете ключ — сообщения не прочитать.** Храните копию отдельно (менеджер паролей).

Чего это не даёт: это **не сквозное шифрование**. Сервер знает ключ и видит текст, поэтому взлом самого
сервера (или кража ключа вместе с базой) раскрывает переписку. Длина сообщения видна по длине шифртекста.
Защита именно от утечки базы и резервных копий.

## Подбор блюд нейросетью

Нейросеть придумывает блюда из продуктов холодильника дома с учётом аллергий, непереносимостей и диет
тех, кто будет есть (`memberIds`, по умолчанию вся семья), и отмечает, что есть в холодильнике, а что докупить.
`allMembers=true` учитывает всю семью. При `allMembers=false` применяются ограничения только из `memberIds`;
пустой список означает отсутствие ограничений. Без флага сохраняется прежнее поведение: пустой список — вся семья.
Выбор применяется к новой AI-подборке. Уже сохранённое избранное не пересчитывается
под выбранных участников. Во время генерации форма выбора участников неактивна.
Модель сначала выбирает разные идеи, затем отдельным запросом подробно расписывает каждую.
Рецепт содержит обязательные этапы подготовки, приготовления и подачи: не менее шести подробных шагов
для блюда и четырёх для напитка, с продуктами каждого шага. Сервер объединяет их с общим составом:
ингредиенты подачи и соусов тоже попадают в теги и покупки. Дополнительный запрос к модели сверяет
состав с текстом всех шагов и добавляет пропущенные продукты до проверки ограничений. Базовые продукты (`staple`) видны в составе,
но считаются уже имеющимися дома. Пометки о покупках в шагах не принимаются.
Перед запросом из списка для модели исключаются продукты, которые не проходят выбранные ограничения.
Сами продукты в холодильнике не изменяются. Модель получает также подсказки о запрещённых группах,
а готовые рецепты повторно проверяются сервером, включая инструкции по приготовлению.
Успешный ответ содержит ровно пять разных проверенных рецептов. `category`: `any` (по умолчанию),
`snack`, `hot`, `cold`, `soup`, `salad`, `bakery`, `dessert`, `drink`, `alcohol`.
Категория `drink` не допускает алкоголь. Категория `alcohol` требует совершеннолетия
автора запроса и всех выбранных участников; возраст проверяется по БД.
Категория передаётся модели вместе с пояснением, блюда должны различаться составом или приготовлением.
Сервер исключает совпадающие названия и рецепты с одновременно одинаковыми составом и инструкциями.
Один набор продуктов может использоваться в разных блюдах, а общие шаги допустимы для разных составов
(например, фруктовых смузи). По отдельности эти совпадения не считаются повтором. Если рецептов не хватает,
он запрашивает недостающие (до трёх попыток генерации со сверкой состава в пределах общего `AI_TIMEOUT`).
Ограничения в питании не ослабляются ради количества: если подборка не заполнена,
API возвращает `ai_incomplete`, а интерфейс предлагает повторить запрос или сменить категорию.
Доступно на тарифе Premium+.

**Провайдер выбирается настройками**. В текущих env-файлах включён GigaChat:

| Провайдер | Настройки модели | Секрет |
|---|---|---|
| `AI_PROVIDER=gigachat` | `GIGACHAT_MODEL=GigaChat-2-Pro`, `GIGACHAT_SCOPE=GIGACHAT_API_PERS`; URL API задаётся кодом | `GIGACHAT_AUTH_KEY` |
| `AI_PROVIDER=openai` | `AI_BASE_URL`, `AI_MODEL`, `AI_JSON_MODE`; совместимый с ожидаемым форматом API | `AI_API_KEY`, если требуется провайдером |

Для GigaChat обязательный ключ проверяется при запуске; его отсутствие останавливает
backend. `AI_REASONING` этому провайдеру не отправляется, режим схемы принудительно
`schema`, параллельность — 1. OAuth-токен получает и обновляет backend.
`AI_REASONING` применяется только к поддерживающему его OpenAI-совместимому провайдеру.
Общий таймаут — `AI_TIMEOUT=5m`. Для запуска без AI: `AI_PROVIDER=openai` и пустой
`AI_BASE_URL`; тогда остальные разделы работают, генерация отвечает 503.

Защита:
- **Модели передаются продукты, ограничения и заметки о питании** — без специально добавляемых имён и почты участников. Свободный текст и сведения об ограничениях могут содержать персональные данные; настройка внешнего AI требует учитывать это.
  Испорченные продукты не отправляются.
- **Ответу нейросети не верим.** Он разбирается строго по JSON-схеме, строки чистятся и обрезаются, а каждое
  блюдо сверяется с ограничениями по словам в названии, ингредиентах и шагах (`recipes/matcher.go`). Блюдо с нарушением отбрасывается
  (в ответе `dropped`). Диеты без явного списка продуктов (кето, сыроедение) проверяет только модель,
  поэтому на странице есть предупреждение «проверяйте состав».
- **Prompt injection.** Названия продуктов и пункты профиля уходят модели отдельным сообщением в виде JSON,
  а инструкция велит считать их данными. Даже если модель поддастся, она умеет только вернуть текст.
- **Лимиты.** 20 запросов в час на человека (не больше 5 подряд), к GigaChat — по одному запросу
  за раз и очередь до 4; остальным — «модель занята» (503).
- Ключ облачного провайдера лежит только на сервере; по `http://` к чужому адресу сервер его не отправит.

## Отправка кодов по почте

### Яндекс SMTP

Текущий отправитель — `famigonoreply@yandex.ru`. Сайт может оставаться на localhost, собственный домен не требуется.

1. Войдите в Яндекс Почту под аккаунтом отправителя. В настройках «Почтовые программы» разрешите доступ почтовым клиентам и использование паролей приложений.
2. В [безопасности Яндекс ID](https://id.yandex.ru/security) откройте «Пароли приложений», выберите тип «Почта» и название Famigo. [Инструкция Яндекса](https://yandex.ru/support/id/ru/authorization/app-passwords). По инструкции новый пароль начинает действовать через 2–3 часа.
3. Добавьте `SMTP_PASSWORD=...` в корневой `secrets.env` без пробелов. Обычный пароль аккаунта не подходит. Не сохраняйте секрет в Git.
4. Перезапустите Go-сервер или выполните из корня `docker compose --env-file .env --env-file secrets.env up -d --build backend`.

В `.env` и `backend/.env` уже настроены:

```dotenv
EMAIL_PROVIDER=smtp
EMAIL_FROM=Famigo <famigonoreply@yandex.ru>
SMTP_HOST=smtp.yandex.ru
SMTP_PORT=465
SMTP_USERNAME=famigonoreply@yandex.ru
```

Порт 587 требует STARTTLS перед передачей пароля; также поддерживается порт 465 с TLS сразу при подключении. Сертификат проверяется, одна попытка подключения ограничена 8 секундами. При сбоях подключения до передачи письма выполняются до трёх попыток с одним и тем же кодом. После начала передачи письма автоматических повторов нет, чтобы не создавать дубликаты. Пароль и код не выводятся в журнал. Без пароля сервер предупреждает об отключённой отправке; регистрация и вход возвращают 503.

Проверить TLS и авторизацию из работающего контейнера без отправки письма:

```bash
docker compose exec backend /app/api mailcheck
```

`SMTP_PASSWORD` передаётся через `env_file: ./secrets.env`: поле `environment` не должно перекрывать его пустым значением. После изменения пароля пересоздайте backend командой запуска выше; простой `restart` не перечитывает окружение контейнера.

Если авторизация отклоняется, проверьте адрес ящика, пароль приложения и разрешение доступа почтовым клиентам. [Справка Яндекса](https://yandex.ru/support/yandex-360/customers/mail/ru/mail-clients/mail-clients-troubleshooting).

Яндекс Почта применяет лимиты и антиспам-проверки; решение предназначено для небольшой тестовой нагрузки. При проверке доставки проверьте папку «Спам».

### Resend (альтернатива)

Для переключения задайте `EMAIL_PROVIDER=resend` и отправителя Resend в используемом `.env`. В Compose значение `EMAIL_FROM` из `environment` имеет приоритет над `env_file`.


В корневом `secrets.env` задайте `RESEND_API_KEY`, а `EMAIL_FROM` — в используемом `.env`.
Docker Compose читает этот файл для бэкенда автоматически; Go при локальном запуске
ищет его в текущей папке и на уровень выше. Применить настройки: `docker compose --env-file .env --env-file secrets.env up -d --build backend`.
Не добавляйте ключ во фронтенд или Git.

С `EMAIL_FROM=onboarding@resend.dev` Resend разрешает тестовые письма только на адрес
владельца аккаунта Resend. Для остальных получателей подтвердите свой домен в Resend
и задайте отправителя на этом домене, например `Famigo <noreply@example.com>`.

`POST /api/auth/register` и `/api/auth/login` возвращают `challengeId`, `email`, `expiresAt`,
`resendAt`, без сессии. `POST /api/auth/email/verify` принимает `challengeId` и шестизначный
`code` и только после проверки выдаёт access-токен и refresh-куку. `POST /api/auth/email/resend`
принимает `challengeId`. Код действует 10 минут, допускается 5 неверных попыток;
повторная отправка — через 60 секунд, предыдущий код заменяется. В базе хранится HMAC
кода с серверным секретом и идентификатором запроса. Без настроенной отправки вход и
регистрация отвечают 503; обхода подтверждения нет.

При регистрации пароль должен содержать минимум 8 символов, хотя бы одну латинскую
букву (`A–Z` или `a–z`), цифру (`0–9`) и специальный символ (например, `!`, `@`, `#`).
Пробел не заменяет специальный символ. Верхняя граница — 72 байта (ограничение bcrypt).
Требования проверяются в форме и в `POST /api/auth/register` до создания заявки и отправки кода.

### Yandex SmartCaptcha

В корневом `secrets.env` задайте собственные ключи:

```dotenv
SMARTCAPTCHA_CLIENT_KEY=ключ_клиента
SMARTCAPTCHA_SERVER_KEY=ключ_сервера
# Необязательно: допустимые имена хостов через запятую, без схемы и порта.
# По умолчанию берутся из ALLOWED_ORIGINS; в разработке добавляются localhost и 127.0.0.1.
# SMARTCAPTCHA_ALLOWED_HOSTS=localhost,127.0.0.1,example.ru
```

В Docker ключи поступают только в backend из `env_file`; после смены пары ключей
пересоздайте backend и обновите страницу. Обычный `restart` не перечитывает окружение.
Пересобирать frontend ради
смены ключей не требуется. Серверный ключ не передаётся браузеру и не хранится в Git.
Если оба ключа отсутствуют, интеграция выключена; один заданный ключ считается ошибкой настроек.
На сайте Яндекса также добавьте разрешённые хосты и оставьте включённой проверку домена.

`GET /api/auth/captcha` возвращает `enabled`, публичный `clientKey` и `required` для входа.
При регистрации виджет обязателен сразу. Первая попытка входа проходит без него;
после неверной почты/пароля сервер требует капчу до успешной проверки данных.
Требование хранится в `login_captcha_gates` по HMAC IP-адреса, сохраняется после
перезапуска и не снимается очисткой cookies, сменой почты или перезагрузкой страницы.
Пользователи за одним внешним IP разделяют это требование.

Формы передают одноразовый `captchaToken` в `POST /api/auth/register` и `/api/auth/login`.
Backend проверяет токен через `https://smartcaptcha.cloud.yandex.ru/validate`, включая
допустимый `host`. Сбой, пустой, неверный или просроченный токен не дают обойти проверку.
Яндекс может вернуть `host` с портом (`localhost:8080`): перед сравнением сервер
извлекает имя хоста, сохраняя проверку разрешённого домена.
После неудачной отправки формы виджет сбрасывается: повторное использование токена запрещено.
После успешной проверки пароля сохраняется обычное подтверждение входа кодом из письма.
Сам виджет поддерживает русский и английский для языков Famigo; подсказки приложения
переведены на все шесть языков. CSP разрешает только необходимые источники SmartCaptcha.

После регистрации подтверждение ведёт к созданию/присоединению к семье. После входа —
на главную, в том числе для аккаунта без семьи. Семейные разделы требуют создания семьи или присоединения.
Запрос подтверждения сохраняется в sessionStorage текущей вкладки, пароль и сам код — нет.

## Сброс пароля

Страница frontend: `/password-reset`, доступна по ссылке «Забыли пароль?» на форме входа.

- `POST /api/auth/password/request`: `{email}` → 202 для зарегистрированной почты; для неизвестной — 422 `account_not_found` без запроса подтверждения. Существование аккаунта проверяется до перехода на форму кода; доставка выполняется асинхронно. Отправляется не чаще раза в минуту, максимум три письма в час на аккаунт; эти ограничения сохраняются в PostgreSQL. Также действует ограничение запросов по IP.
- `POST /api/auth/password/verify`: `{challengeId, code}` → одноразовый `resetToken` после проверки шестизначного кода. Не более пяти неверных попыток, срок — десять минут от выдачи кода.
- `POST /api/auth/password/reset`: `{challengeId, resetToken, password, confirmPassword}` → 204. В транзакции обновляется bcrypt-хеш, отзываются все refresh-сессии и погашаются незавершённые коды пользователя.

Код хранится как HMAC. После проверки его хеш заменяется HMAC случайного 256-битного токена; старый код больше не принимается. Токен разрешает только смену пароля, хранится в памяти страницы и не продлевает исходные десять минут. Обновление страницы начинает сценарий заново. Новый запрос не блокирует вход и не меняет пароль до успешного завершения сброса.

После сохранения показывается подтверждение с возвратом на обычную форму входа. Автоматическая авторизация не выполняется. Неизвестная почта возвращает отдельную ошибку: это осознанно позволяет определить наличие аккаунта по адресу. Для ограничения перебора действует общий лимит запросов по IP. При ошибке доставки сервер пишет предупреждение без почты, кода и токена.

Проверка полного сценария на выделенной тестовой базе: `FAMIGO_TEST_DATABASE_URL=... go test ./internal/auth -run TestPasswordResetFlow -v`. Используется поддельная доставка, реальные письма тест не отправляет.

## Регистрация до подтверждения почты

`POST /api/auth/register` создаёт только временную заявку в `pending_registrations`: имя, почта, дата рождения, bcrypt-хеш пароля, версия соглашений и HMAC кода. В `users`, `user_settings`, `consents` и `refresh_tokens` записи не создаются.

Проверка выполняется прежним `POST /api/auth/email/verify`. Только действующий код создаёт пользователя с подтверждённой почтой, настройки, согласия и сессию одной транзакцией. Заявка после этого удаляется. Неверный, просроченный или использованный код пользователя не создаёт.

Код действует 10 минут, допускает пять ошибок; повторная отправка — через минуту. Новая регистрация на тот же адрес заменяет прежнюю заявку после паузы, но не существующий аккаунт. Просроченные заявки очищаются при последующих запросах регистрации. Ошибка отправки откатывает заявку и не оставляет пользователя в базе.

Ранее созданные аккаунты эта миграция не удаляет.

## GigaChat

Выбран `AI_PROVIDER=gigachat`, модель `GigaChat-2-Pro`, Scope `GIGACHAT_API_PERS`. Добавьте `GIGACHAT_AUTH_KEY='ключ авторизации'` в корневой `secrets.env`. Временный access token вручную сохранять не нужно: backend получает его через OAuth и обновляет в памяти. Ключ не передаётся браузеру и не записывается в журнал. Секрет передаётся через Compose env_file.

Настройки `GIGACHAT_MODEL` и `GIGACHAT_SCOPE` находятся в обычных env-файлах. Адрес API — `https://api.giga.chat/v1`. Размышления reasoning_effort для этого провайдера не отправляются; JSON-схема передаётся в формате GigaChat. Ограничение — один запрос к модели одновременно. Проверки рецептов остаются на сервере.

TLS проверяется с официальными сертификатами из [инструкции GigaChat](https://developers.sber.ru/docs/ru/gigachat/certificates), загруженными с gu-st.ru в `internal/ai/certs`. Они включены только в HTTP-клиент GigaChat; системное хранилище не меняется. При обновлении сертификатов нужно обновить файлы и пересобрать backend.


Квоты и условия внешнего GigaChat определяются проектом провайдера; тариф Famigo не включает отдельную квоту его API. Продукты, ограничения и пожелания передаются внешнему провайдеру; персональные сведения в свободном тексте автоматически не обезличиваются.

## Избранное и расширенные чаты

### Возраст и алкоголь

`GET /api/me` возвращает вычисленный `canUseAlcohol`: 18 лет по дате рождения в БД
и московскому времени. Без даты или до совершеннолетия флаг ложный. Категория
`alcohol` скрывается в интерфейсе; API холодильника фильтрует такие продукты и
запрещает несовершеннолетнему их добавление/изменение/удаление. Известные названия
спиртного распознаются и при подмене категории.

Генерация читает возраст автора и выбранных едоков из БД. Клиент не может передать
собственный `AllowAlcohol`. Если не все совершеннолетние, спиртное исключается из
входных продуктов, добавляется запрет модели, ответ повторно проверяется по
названию, ингредиентам и шагам. `drink` всегда без алкоголя. Проверка терминов
не гарантирует безошибочное распознавание состава. Дата рождения задаётся в
профиле; проверка документов не реализована.

### Личное избранное

`GET/POST /api/me/recipes`, `DELETE /api/me/recipes/:favoriteID` — личные сохранённые
рецепты. GET возвращает до 500 последних записей; повторное сохранение одинакового
JSON определяется SHA-256 отпечатком. Чтение и удаление ограничены владельцем;
отдельной проверки Premium+ у этого API нет. Генерация проверяет тариф сервером.

### Сообщения и вложения

`POST /api/families/:familyID/chats/:chatID/rich` принимает текст с `replyId`, рецепт
в `recipe` либо пересылку по `sourceChatId` и `forwardId`. Ответ хранит краткий снимок
цитаты; пересылка требует доступа к обоим чатам. `POST .../media` принимает multipart
`file` (один файл либо повторяющиеся поля для альбома); каждый файл до 25 МиБ.
`GET .../media/:mediaID` требует Bearer-токен и членство в чате.
Форматы: JPEG/PNG/GIF/WebP и MP4/WebM/MOV. MIME определяется по содержимому; HTML и
SVG отклоняются. HEIC преобразуется в JPEG во frontend до отправки.

Файлы хранятся в `chat_media` как двоичные данные PostgreSQL; сообщение, детали и
все его вложения записываются одной транзакцией. При пересылке создаётся отдельная копия
для целевого чата: удаление оригинала не лишает доступа к пересланной копии.

AES-256-GCM защищает текст, вложения и `details` при настроенном `MESSAGE_KEYS`. Общая тарифная квота медиа чата
не реализована. Загрузка аватарки семьи также пока не реализована.

### Голосовые и видеокружочки

Загрузка записей использует тот же endpoint медиа: multipart-поля `kind`
(`voice` или `round`) и `duration` (секунды). Метаданные сохраняются в
`details.media` и сохраняются при пересылке. Добавлены аудио WebM, MP4, OGG,
MP3 и WAV. MIME определяется по содержимому, размер ограничен 25 МиБ;
для `round` сервер отклоняет заявленную длительность свыше 60 секунд.
Длительность в метаданных поступает от клиента, сервер не декодирует файл
для независимой проверки времени. Клиент останавливает запись по таймеру.
Аудио и видеокружочки используют те же проверки доступа, шифрование и удаление,
что остальные вложения. Permissions-Policy разрешает микрофон только своему origin.

### Альбомы и подписи

`POST /api/families/:familyID/chats/:chatID/media` принимает от 1 до 10
multipart-файлов с повторяющимся полем `file`, общую подпись `text` (до 2000
символов) и необязательный `replyId`. Каждый файл — до 25 МиБ, сумма — до 100 МиБ;
лимит тела этого маршрута и nginx — 101 МиБ с запасом на multipart. Для остальных
загрузок сохраняется прежний серверный лимит. MIME всех файлов проверяется до
записи; сообщение и все `chat_media` сохраняются одной транзакцией, поэтому
ошибка в одном файле не создаёт частичный альбом. Одиночный файл хранится в
`details.media`, альбом — в `details.mediaItems`, подпись — в `details.caption`.
Старые сообщения совместимы; новая миграция не нужна. Пересылка копирует все
файлы с новыми ID и повторным шифрованием, сохраняя подпись; удаление оригинала
не затрагивает пересланный альбом. `kind=voice|round` допустим только для одного файла.

Метаданные `media` и каждого элемента `mediaItems` содержат `id`, `mime`, `name`;
у записей добавлены `kind` и `duration`. Клиент не задаёт серверные ID вложений
и MIME из заголовка не считается доказательством формата. Подпись передаётся
также в `message.text`; без подписи там остаются имена для текстового представления,
но интерфейс сообщения показывает название файла только в просмотрщике.
Успешная загрузка возвращает 201 с одним сообщением. Неверный файл, количество,
подпись или параметры записи возвращают 400 без частично сохранённого альбома.

Просмотр со стрелками использует обычный `GET .../media/:mediaID` и список уже
загруженных сообщений; отдельного серверного поиска всей медиатеки чата пока нет.
Отмена HTTP-загрузки при переключении и освобождение Blob URL выполняются клиентом.

### Удаление и личное скрытие

Удаление сообщения очищает его текст и `details`, выставляет `deleted_at` и
физически удаляет связанные строки `chat_media` одной транзакцией. Служебная
запись сообщения остаётся; исходные фото и видео из рабочей БД удаляются.
Миграция `0023_purge_deleted_chat_media.sql` очищает вложения сообщений,
удалённых предыдущей реализацией. Пересланные копии не затрагиваются.
Это логическое удаление записей PostgreSQL, а не гарантированное стирание
секторов диска: старые резервные копии и WAL могут сохранять прежние данные
до окончания своего срока хранения.

`DELETE /api/families/:familyID/chats/:chatID/messages/:messageID?scope=me`
скрывает собственное сообщение только для аккаунта через `hidden_chat_messages` (миграция
0024). История, последнее сообщение и счётчики исключают скрытые сообщения;
событие `hidden` получают только подключения этого пользователя. `scope=all`
(также значение по умолчанию) удаляет для всех с проверкой авторства и очисткой
вложений. Оба варианта проверяют авторство: попытка удалить чужое сообщение
возвращает 404 без изменения истории, скрытых сообщений или вложений.
Неизвестный `scope` возвращает 400.

### Статус набора текста

WebSocket принимает команду `typing` с `familyId`, `chatId`, `typing` и
проверяет членство отправителя в чате. Ответ `typing` содержит снимок
`userIds` печатающих участников. Статус хранится в памяти отдельно для каждого
подключения, истекает через 6 секунд без обновлений и снимается при отключении.
Несколько вкладок одного пользователя дают одно имя; отключение одной вкладки
не скрывает набор в другой. Ограничение частоты команд действует и на набор.

## Миграции новых функций

| Миграция | Изменение |
|---|---|
| `0018_favorites_and_chat_media.sql` | `recipe_favorites`, `chat_media`, JSONB `messages.details` |
| `0019_alcohol_category.sql` | категория алкогольных продуктов |
| `0020_message_views.sql` | отдельные просмотры сообщений `message_views` |
| `0021_login_captcha.sql` | сохраняемое требование капчи `login_captcha_gates` |
| `0022_family_admin_seniority.sql` | дата назначения администратора и порядок автоматической передачи владельца |
| `0023_purge_deleted_chat_media.sql` | очистка вложений сообщений, логически удалённых предыдущей реализацией |
| `0024_hidden_chat_messages.sql` | личное скрытие собственных сообщений в `hidden_chat_messages`, ключ `(user_id, message_id)` |

Альбомы, подписи, голосовые и кружочки используют существующие `messages.details`
и `chat_media`; для них отдельная миграция не нужна. Набор текста хранится в памяти
hub и тоже не создаёт таблицы. При обновлении API миграция 0023 действительно
удаляет оставшиеся вложения уже удалённых сообщений из рабочей БД; перед переносом
обновления сохраняйте резервную копию и ключи шифрования. Миграция 0024 хранит только
связь аккаунта и сообщения, не дублируя текст или файлы.

При выходе владельца или удалении его аккаунта триггер `pass_family_ownership`
передаёт роль администратору с самым ранним `admin_assigned_at`. Без администраторов
выбирается участник с самым ранним `joined_at`; пустая семья удаляется.
Снятие роли администратора очищает дату, новое назначение записывает новую.
Повторное сохранение той же роли и смена дома дату не меняют. При равных датах
используются `joined_at`, затем `user_id` для однозначного выбора.
У существовавших до миграции администраторов дата назначения неизвестна (`NULL`):
для них при сравнении используется `joined_at`. Передача и выход выполняются
в транзакции; выбранный преемник получает все права владельца, включая управление
семейной подпиской.

Миграции применяются автоматически при старте API. Для обновления существующей
копии сохраняйте тома БД и аватаров; ручное удаление базы или создание таблиц
через pgAdmin для этих изменений не нужны. Исторические значения `last_read_at`
не превращаются в просмотры отдельных сообщений: новые отметки появляются при
фактическом просмотре. Новые функции входа используют уже существующие аккаунты.

## Доступ к домам после окончания подписки

Подписка одна на семью (`family_id`); плательщик не определяет доступ участников. Middleware `subscriptions.RequireHomeAccess` после проверки членства защищает все маршруты с `:homeID`, включая дела, продукты и AI. Сначала проверяется принадлежность дома семье (404), затем действующий тариф (403 `home_plan_locked`). Доступны первые `MaxHomes` домов по `created_at, id`; нулевой лимит Premium+ означает все дома. `GET /homes` возвращает все карточки с флагом `locked`; данные не удаляются. После окончания срока применяется Free независимо от настройки продления; реальных автоматических платежей пока нет.
