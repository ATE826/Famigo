# <img src="_docs/assets/famigo-logo.png" alt="Логотип Famigo" width="40" height="40" align="absmiddle"> Famigo

**Всё важное для семьи в одном месте.**

Famigo — веб-приложение для совместной организации семейной жизни. Участники семьи ведут общий бюджет, планируют события, распределяют домашние дела, следят за продуктами и общаются в семейном и личных чатах.

Основная единица приложения — семейная группа. Она объединяет участников с разными правами, дома, продукты, финансовые операции, события и переписку. Часть данных связана с конкретным домом, остальные относятся ко всей семье.

Проект развивается как учебный fullstack-продукт. Основные сценарии работают через Go API и PostgreSQL. Для будущих возможностей подготовлены демонстрационные экраны; их статус описан отдельно.

## Возможности

### Реализовано с сохранением на сервере

| Раздел | Что доступно |
| --- | --- |

| Профиль | Имя, дата рождения, телефон, аватар, пищевые предпочтения и ограничения без повторного чекбокса; условия включены в основное согласие |

| Холодильник | Продукты каждого дома: категории, количество, единицы измерения и сроки годности; поиск и фильтрация в интерфейсе |
| Бюджет | Добавление доходов и расходов, привязка к дому, история операций, фильтры и сводные показатели |

| Уведомления | Лента, счётчик непрочитанных, отметка одного или всех уведомлений прочитанными, настройки получения |


Раздел рецептов объединяет встроенный каталог и серверный AI-подбор по продуктам дома с учётом пищевых ограничений. Доступ к разделу в текущем интерфейсе предоставляется на Premium+.

Главная страница собирает сводку по бюджету, событиям, продуктам, домашним делам и чатам. Интерфейс поддерживает мобильные и настольные экраны.

## Пользовательский сценарий

1. Начать регистрацию: указать имя, почту, пароль и дату рождения, отдельно принять соглашение и согласие на обработку данных. До проверки кода данные находятся во временной заявке `pending_registrations`, аккаунта в `users` ещё нет.
2. Подтвердить почту шестизначным кодом из письма: пользователь, настройки, согласия и сессия создаются одной транзакцией. Код требуется также при входе с паролем.
3. Создать семью или присоединиться по приглашению. Аккаунту без семьи доступна главная страница; семейные разделы требуют вступления в группу.
4. Добавить дома, назначить жильцов и пригласить остальных участников.
5. Вести бюджет, календарь, продукты и домашние дела; обсуждать их в чатах.
6. При необходимости оформить демонстрационную подписку Premium+ и подобрать блюда по содержимому холодильника.

В семье есть три роли: **Owner**, **Admin** и **Member**. Владелец и администраторы управляют домами, участниками и подпиской в пределах своих полномочий. Права проверяются сервером; скрытие кнопки в интерфейсе не заменяет проверку доступа.

Сервер поддерживает членство в нескольких семьях. Текущий интерфейс загружает первую семью из списка; отдельного переключателя семей пока нет.

## Архитектура

```text
Браузер
  └─ nginx :8080
      ├─ /Famigo/ → React SPA
      └─ /api/    → Go API
                      ├─ PostgreSQL
                      ├─ файлы аватаров
                      ├─ Gmail SMTP / Resend → письма с кодами
                      └─ Ollama / внешний AI API → рецепты
```

Frontend обращается к API по относительному адресу `/api`. В разработке HTTP-запросы и WebSocket проксирует Vite, в Docker — nginx. Приложение использует базовый путь `/Famigo/`.

Серверные модули следуют схеме **handler → service → repository**: обработчик проверяет HTTP-запрос, сервис выполняет бизнес-правила, репозиторий работает с БД. Подключение модулей находится в `backend/internal/server/routes.go`.

`frontend/src/store/DataProvider.jsx` загружает профиль и семейные данные, предоставляет действия страницам и обрабатывает события чата. `frontend/src/api/mappers.js` преобразует серверные форматы в данные интерфейса.

## Запуск через Docker

Стандартная конфигурация поднимает frontend с nginx, Go API, PostgreSQL, Ollama и одноразовый загрузчик модели `ollama-init`.

### Требования

- Docker с Compose 2.30 или новее.
- Для стандартной конфигурации с `gpus: all` — NVIDIA GPU, доступная контейнерам. На Windows нужны Docker Desktop с WSL 2 и соответствующий драйвер.
- Gmail с двухэтапной аутентификацией и паролем приложения для отправки кодов.
- Свободное место для Docker-образов, базы и выбранной AI-модели.

### Подготовка

Создайте в корне проекта файл `secrets.env` со своими значениями:

```dotenv
POSTGRES_PASSWORD='<пароль базы данных>'
DATABASE_URL='postgres://famigo:<URL-кодированный пароль>@localhost:15432/famigo?sslmode=disable'
DOCKER_DATABASE_URL='postgres://famigo:<URL-кодированный пароль>@db:5432/famigo?sslmode=disable'
JWT_SECRET='<случайный секрет длиной не менее 32 символов>'
MESSAGE_KEYS='1:<случайный ключ из 32 байт в base64>'
SMTP_PASSWORD='<пароль приложения Gmail без пробелов>'
```

Заполнители в угловых скобках нужно заменить. В URL закодируйте специальные символы пароля, например `@` → `%40`, `#` → `%23`, `$` → `%24`; `POSTGRES_PASSWORD` оставьте исходным. Resend и `RESEND_API_KEY` нужны только при выборе `EMAIL_PROVIDER=resend`. В `.env` и `backend/.env` настроен отправитель `famigonoreply@gmail.com`. Используйте пароль приложения этого аккаунта, обычный пароль Gmail не подходит. Файл `secrets.env` исключён из Git. Ключ для `MESSAGE_KEYS` можно получить командой `openssl rand -base64 32`, если OpenSSL установлен.

### Запуск

Из корня репозитория:

```bash
docker compose up -d --build
```

Откройте [http://localhost:8080/Famigo/](http://localhost:8080/Famigo/). Проверка API: [http://localhost:8080/api/health](http://localhost:8080/api/health).

Таблицы создаются автоматически при запуске backend. Модель скачивается параллельно с запуском приложения; AI-подбор станет доступен после завершения загрузки.

```bash
# Состояние сервисов и сообщения backend
docker compose ps
docker compose logs --tail=100 backend

# Прогресс загрузки и установленные модели
docker compose logs -f ollama-init
docker compose exec ollama ollama list

# Остановка с сохранением данных
docker compose down
```

База, аватары и модели сохраняются в томах `famigo-db`, `famigo-uploads` и `famigo-ollama`. Команда `docker compose down -v` удаляет эти данные.

Без `SMTP_PASSWORD` сервер запускается с предупреждением, а регистрация и вход отвечают `503 email_unavailable`. Настройка Gmail описана в [документации backend](backend/README.md#gmail-smtp).

## Локальная разработка

### Backend

Нужны Go в соответствии с `backend/go.mod` (сейчас `go 1.27.1`, toolchain `go1.27.3`) и PostgreSQL. В Docker используется PostgreSQL 17.

Добавьте в корневой `secrets.env` строку подключения к своей локальной базе:

```dotenv
DATABASE_URL=postgres://famigo:<URL-кодированный пароль>@localhost:15432/famigo?sslmode=disable
```

Пример использует базу из текущего Compose. Для отдельного PostgreSQL укажите его фактический порт, обычно `5432`. Не запускайте Docker-frontend одновременно с локальным Go-сервером на порту `8080`: сначала остановите `frontend` и `backend`, оставив `db`. Для специальных символов в пароле используйте URL-кодирование. База и пользователь должны существовать до запуска; таблицы создадут миграции. Для входа также нужны почтовые настройки из раздела выше.

```bash
cd backend
go run ./cmd/api
```

Сервер читает `backend/.env` и ищет `secrets.env` в текущей папке и на уровень выше. API по умолчанию слушает `http://localhost:8080`.

### Frontend

Нужны Node.js и npm. Для ветки Node.js 22 минимальная версия — 22.12; точный диапазон совместимости задаётся зависимостями Vite. В другом терминале:

```bash
cd frontend
npm ci
npm run dev
```

Откройте [http://localhost:5173/Famigo/](http://localhost:5173/Famigo/). Vite перенаправляет `/api` и WebSocket на `http://localhost:8080`.

Для AI-рецептов запустите Ollama отдельно и установите модель, указанную в `backend/.env`. При разработке остальных разделов модель не обязательна. Стандартный Compose запускает Ollama с GPU без отдельного профиля; для работы без GPU используйте локальный запуск либо адаптируйте Compose под свою среду.

## Настройки

| Где | Назначение |
| --- | --- |
| `.env` | Режим, публичный адрес и AI-настройки для Docker Compose |
| `backend/.env` | Настройки backend при запуске из папки `backend` |
| `secrets.env` | Пароли, токены и ключи; в Git не включается |
| Переменные окружения | Переопределение настроек Go-процесса |

При локальном запуске Go приоритет такой: окружение процесса → `.env` → `secrets.env`. Путь к внешнему файлу секретов можно указать через `SECRETS_FILE`.

Compose получает значения подстановок из `--env-file` и окружения, затем передаёт настройки контейнерам. При изменении настроек используйте ту же команду запуска с обоими `--env-file`. В контейнере используется `DOCKER_DATABASE_URL`, если задан; иначе `DATABASE_URL` строится из `POSTGRES_PASSWORD`. Отдельная локальная строка `DATABASE_URL` его не заменяет. Для паролей со спецсимволами задайте URL-кодированный пароль в обеих строках подключения: `DOCKER_DATABASE_URL` с адресом `db:5432`, `DATABASE_URL` с адресом `localhost:15432`. Сам `POSTGRES_PASSWORD` хранится без URL-кодирования; одинарные кавычки в env-файле предотвращают подстановки символа `$`. Смена пароля в файле сама по себе не меняет пароль пользователя в уже созданной базе.

| Переменная | Назначение |
| --- | --- |
| `APP_ENV` | `development` или `production` |
| `PUBLIC_URL` | Публичный адрес в Compose; используется для разрешённого Origin |
| `DATABASE_URL` | Подключение Go API при запуске вне Docker |
| `DOCKER_DATABASE_URL` | Строка подключения внутри Compose, обычно к `db:5432`; пароль URL-кодирован |
| `POSTGRES_PASSWORD` | Исходный пароль пользователя БД; изменение файла не меняет пароль существующей БД |
| `JWT_SECRET` | Секрет подписи access-токенов |
| `MESSAGE_KEYS` | Версионированные ключи шифрования сообщений в базе |
| `EMAIL_PROVIDER`, `EMAIL_FROM` | Провайдер (`smtp` или `resend`) и отправитель |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_USERNAME`, `SMTP_PASSWORD` | SMTP-сервер, порт, логин и пароль приложения |
| `RESEND_API_KEY` | Ключ альтернативного провайдера Resend |
| `COOKIE_SECURE`, `COOKIE_SAMESITE` | Параметры refresh-cookie |
| `ALLOWED_ORIGINS`, `TRUSTED_PROXIES` | Разрешённые Origin и доверенные прокси backend |
| `ACCESS_TOKEN_TTL`, `REFRESH_TOKEN_TTL` | Сроки токенов; по умолчанию 15 минут и 30 дней |
| `RATE_LIMIT`, `AUTH_RATE_LIMIT` | Ограничения частоты запросов |
| `UPLOAD_DIR` | Папка аватаров |
| `LEGAL_VERSION` | Версия согласий при регистрации; по умолчанию `2026-11-14.2` в Go-конфигурации |
| `DEMO_PAYMENTS` | Разрешение оформить подписку без оплаты |
| `AI_BASE_URL`, `AI_MODEL`, `AI_API_KEY` | Адрес, модель и ключ AI-провайдера |
| `AI_TIMEOUT`, `AI_MAX_CONCURRENT` | Общее время ожидания и параллельность AI-запросов |
| `AI_JSON_MODE`, `AI_REASONING` | Режим JSON-ответа и настройка reasoning провайдера |

Для production задайте постоянные `JWT_SECRET` и `MESSAGE_KEYS`, настройте HTTPS и `COOKIE_SECURE=true`, отключите `DEMO_PAYMENTS`. В текущем Compose последние два значения задаются явно: одной смены `APP_ENV` недостаточно. HTTPS должен обеспечивать внешний прокси или другая инфраструктура перед nginx.

## Подключение к БД через pgAdmin

Для pgAdmin на компьютере используйте: сервер `127.0.0.1`, порт `15432`, база `famigo`, пользователь `famigo`. Пароль — исходное значение `POSTGRES_PASSWORD` без окружающих кавычек, а не URL-кодированная строка. В Docker используется адрес `db:5432`. Порт опубликован только на loopback; используйте актуальный Docker Engine (28.0.0 или новее для исправления прежних ограничений loopback-публикации).

В pgAdmin: **Register → Server → Connection**. Таблицы: **Databases → famigo → Schemas → public → Tables**; просмотр: **View/Edit Data**. Пользователь `famigo` имеет широкие права — изменения из pgAdmin затрагивают реальные данные приложения.

При смене пароля существующей БД:

1. Измените пароль роли `famigo` через **Login/Group Roles → famigo → Properties → Definition → Password** и сохраните.
2. Обновите `POSTGRES_PASSWORD`, `DATABASE_URL` и `DOCKER_DATABASE_URL` в `secrets.env`. В двух URL пароль должен быть URL-кодирован, в первом значении — исходный. Одинарные кавычки предотвращают подстановки символа доллара в Compose.
3. Выполните `docker compose --env-file .env --env-file secrets.env up -d db backend` и обновите сохранённый пароль pgAdmin.

Пересоздание контейнера сохраняет том, но не меняет пароль в уже инициализированном PostgreSQL. Не удаляйте том ради смены пароля. Внутренняя проверка `psql` через Unix-сокет может работать с `trust` и не доказывает правильность пароля для сетевого подключения.

## Подбор рецептов

На тарифе Premium+ пользователь выбирает дом, число порций, категорию блюда и участников, чьи ограничения нужно учитывать. Сервер получает пригодные продукты холодильника и формирует подборку из пяти разных рецептов.

Генерация включает выбор идей, подробное описание приготовления и дополнительную сверку ингредиентов со всеми шагами. В ответе отмечается, какие продукты есть дома и что нужно докупить. Сервер проверяет ограничения и повторы; если полноценную подборку получить не удалось, возвращается ошибка.

В стандартном Compose используется Ollama с моделью `gemma4:e4b`. При локальном запуске адрес — `http://localhost:11434/v1`, внутри Compose — `http://ollama:11434/v1`. Можно настроить внешний OpenAI-совместимый API; его ключ остаётся на сервере. Пустой `AI_BASE_URL` отключает AI-подбор.

Генерация может занимать несколько минут. Ответы модели дополнительно проверяются приложением, однако пользователю всё равно следует проверять состав и инструкции, особенно при аллергиях. Имена и почта участников не включаются в запрос; модели передаются продукты, ограничения и текстовые пожелания к питанию.

## Тарифы

В Famigo три тарифа: **Free**, **Premium** и **Premium+**. Подписка оформляется на семейную группу: её возможности получают все участники этой семьи. Отдельная подписка для каждого пользователя не требуется. Для другой семейной группы тариф определяется независимо.

Текущие цены и ограничения заданы в `frontend/src/utils/plans.js` и `backend/internal/subscriptions/plans.go`. Платёжный провайдер пока не подключён: ниже описаны параметры продукта и фактически реализованное поведение демонстрационной подписки.

### Free — базовое семейное пространство

Бесплатный тариф действует по умолчанию, если у семьи нет активной платной подписки. Он позволяет пользоваться основными разделами: участниками, домами, домашними делами, холодильником, бюджетом, календарём, чатами и уведомлениями.

Семья может создать до двух домов. Например, квартиру и дачу: у каждого дома будет собственный набор продуктов и дел. При попытке добавить третий дом сервер вернёт ошибку ограничения тарифа.

На Free недоступны раздел рецептов, геолокация, история мест, check-in и QR-сканер чеков. При этом расходы можно добавлять вручную, а продукты — учитывать без подбора блюд.

### Premium — дополнительный дом и демонстрационные функции заботы

Premium стоит **249 ₽ за месяц** или **2 490 ₽ за год**. Годовая стоимость на 498 ₽ ниже двенадцати месячных периодов — экономия около 16,7%, в интерфейсе округляется до 17%. Средняя стоимость при годовом периоде — 207,50 ₽ в месяц.

Тариф включает базовые функции Free и увеличивает лимит до трёх домов. В интерфейсе также открываются геолокация, сохранённые места, история мест за семь дней и «Я в порядке»; лимит локальной галереи увеличивается до 10 ГиБ.

Главное реализованное серверное отличие от Free — возможность создать третий дом. Геолокация и функции заботы пока демонстрационные. Раздел рецептов и QR-сканер на Premium остаются закрыты.

### Premium+ — рецепты и расширенные лимиты

Premium+ стоит **499 ₽ за месяц** или **4 990 ₽ за год**. Годовой период на 998 ₽ дешевле двенадцати месячных — экономия около 16,7%. Средняя стоимость — примерно 415,83 ₽ в месяц. Цена Premium+ в исходном коде отмечена как предварительная.

Тариф включает возможности Premium и добавляет:

- Создание домов без числового ограничения со стороны тарифа.
- Раздел готовых рецептов и AI-подбор пяти блюд из продуктов выбранного дома.
- Учёт пищевых ограничений всей семьи или выбранных участников при подборе.
- Выбор категории блюда и числа порций, подробные инструкции и список недостающих ингредиентов.
- QR-сканер для заполнения суммы и даты расхода.
- Историю демонстрационных мест за 30 дней и лимит локальной галереи 100 ГиБ.

Для AI-подбора дополнительно нужна настроенная и доступная модель на сервере. Подписка не отменяет ограничения частоты запросов, очередь к модели и общий таймаут генерации.

### Оформление и управление

Тариф выбирается на странице `/premium`: пользователь переключает месячный или годовой период и подтверждает оформление в диалоге без повторного чекбокса соглашения. В текущем режиме банковские данные не запрашиваются, деньги не списываются.

| Действие | Кто может выполнить |
| --- | --- |
| Оформить или сменить платный тариф | Владелец или администратор семьи |
| Отключить или включить настройку продления | Владелец, администратор или пользователь, записанный плательщиком |
| Пользоваться доступными возможностями | Все участники семьи в пределах своих обычных прав |

Подписка расширяет доступные функции, но не повышает роль участника: например, Member не получает права создавать дома только благодаря Premium+.

При оформлении сервер сохраняет тариф, период, пользователя-плательщика и дату окончания: через один календарный месяц или год от момента запроса. Повторное оформление или смена тарифа заменяет текущую подписку и отсчитывает срок заново от этого момента. Перерасчёт остатка периода, доплаты и возвраты не реализованы.

### Продление, окончание срока и возврат на Free

Отключение продления сохраняет текущий тариф до конца установленного срока. Его можно снова включить до истечения подписки. Сейчас это изменение настройки в базе: механизма автоматической оплаты и продления срока нет. Даже при включённом продлении после окончания срока действующим тарифом становится Free, если подписка не оформлена заново.

При истечении подписки существующие дома, продукты, операции и переписка автоматически не удаляются. Если домов уже больше двух, они сохраняются, но добавить новый сверх лимита Free нельзя. Доступ к AI-подбору сервер проверяет по действующему тарифу.

Сервер пересчитывает активный тариф при обращении к подписке и защищённым тарифным операциям. Интерфейс получает подписку при загрузке семейных данных и её изменении; отдельного таймера обновления тарифа в открытой вкладке нет.

### Что проверяется сервером

Лимит создания домов и право пользоваться AI-рецептами проверяются на backend. Создание домов выполняется с блокировкой семьи, чтобы параллельные запросы не обходили ограничение. Тарифные ограничения демонстрационной карты, check-in, сканера и локальной галереи применяются интерфейсом; серверных API этих разделов пока нет.

Оформление работает только при `DEMO_PAYMENTS=true`. При выключенном режиме API возвращает `501 payments_unavailable`: настоящая покупка пока недоступна. Для production демо-оформление нужно отключить явно в конфигурации Compose.

## API и модель данных

API использует префикс `/api`, JSON и `Authorization: Bearer <accessToken>` для защищённых запросов. Обновление сессии выполняется через HttpOnly cookie. Денежные суммы на сервере хранятся целым числом копеек; даты передаются как `YYYY-MM-DD`, дата и время — RFC 3339.

| Группа | Назначение |
| --- | --- |
| `/api/health` | Готовность API и подключение к БД |
| `/api/auth/*` | Регистрация, вход, коды почты, обновление и завершение сессий |
| `/api/me` и вложенные адреса | Профиль, аватар, пароль, питание, настройки |
| `/api/families` | Список семей, создание и присоединение |
| `/api/families/:familyID/*` | Участники, дома, продукты, бюджет, календарь, чаты, подписка и рецепты |
| `/api/notifications` и вложенные адреса | Лента и отметки прочтения |
| `/api/chats/ws-ticket`, `/api/chats/ws` | Одноразовый билет и WebSocket |

Регистрация и вход возвращают запрос подтверждения (`challengeId`); токены выдаются после `POST /api/auth/email/verify`. WebSocket открывается с одноразовым билетом на 30 секунд. При обрыве frontend переподключается и обновляет данные чата.

Основные группы таблиц:

- Пользователи и временные регистрации: `users`, `pending_registrations`, `user_settings`, `user_food_prefs`, `consents`, `verification_codes`, `refresh_tokens`.
- Семья и быт: `families`, `family_members`, `family_invites`, `homes`, `home_tasks`, `products`.
- Финансы и планы: `transactions`, `events`, `event_members`, `subscriptions`.
- Общение: `chats`, `chat_members`, `messages`, `notifications`.

SQL-миграции вшиваются в Go-приложение и выполняются при запуске под блокировкой PostgreSQL. Таблицы приложения создаются SQL, а не GORM AutoMigrate. Миграции геолокации, безопасности и галереи пока пустые. `backend/api/openapi.yaml` также является пустой заготовкой: готовой Swagger/OpenAPI-спецификации сейчас нет.

## Безопасность

- Пароли хешируются bcrypt; коды подтверждения действуют 10 минут, допускают пять неверных попыток, в базе хранится HMAC кода. На вход действуют лимиты по IP и почте; отдельной блокировки аккаунта на 15 минут после пяти неверных паролей сейчас нет.
- Сброс пароля проверяет наличие аккаунта до формы кода и возвращает `422 account_not_found` для неизвестного адреса. Для существующего адреса отправка асинхронная: `202` не гарантирует доставку. После сброса прежние сессии завершаются; автоматического входа нет.
- Access-токен хранится в памяти frontend, refresh-токен — в HttpOnly cookie, в БД — его хеш. Refresh-токены ротируются; сервер проверяет актуальность сессии.
- Для семейных запросов проверяются членство и права. Изменения ролей и ряд операций с лимитами выполняются в транзакциях с блокировками.
- Используются параметризованные запросы, отдельные структуры входных данных и отклонение неизвестных JSON-полей.
- Настроены ограничения частоты и размера запросов, проверка Origin, защитные HTTP-заголовки и CSP.
- Аватары проверяются и перекодируются в JPEG перед сохранением.
- При заданном `MESSAGE_KEYS` сообщения шифруются в базе с AES-256-GCM. Сервер расшифровывает текст для участников чата; это шифрование хранения, а не сквозное шифрование. В production ключ обязателен; его нужно сохранять отдельно от базы.
- В Docker backend и nginx работают без root. PostgreSQL опубликован только на `127.0.0.1:15432` для локального pgAdmin; внутри Docker используется `db:5432`.

Подробности реализации и ротации ключей описаны в [документации backend](backend/README.md).

## Проверки

Frontend:

```bash
cd frontend
npm run lint
npm run build
```

Backend:

```bash
cd backend
go test ./...
```

Go-тесты охватывают авторизацию, валидацию, middleware, шифрование, обработку аватаров, роли, тарифы, бюджет и AI-рецепты. Некоторые тесты используют временные локальные HTTP-серверы.

Интеграционный тест требует отдельной пустой PostgreSQL-базы и переменной `FAMIGO_TEST_DATABASE_URL`. Пример для PowerShell из папки `backend`:

```powershell
$env:FAMIGO_TEST_DATABASE_URL = 'postgres://famigo:<пароль>@localhost:15432/famigo_test?sslmode=disable'
go test ./internal/server -v
Remove-Item Env:FAMIGO_TEST_DATABASE_URL
```

Тест применяет миграции и изменяет данные: используйте только выделенную тестовую базу. Без переменной этот сценарий пропускается. Необязательные проверки настоящей AI-модели запускаются с `FAMIGO_TEST_AI_URL` и, при необходимости, `FAMIGO_TEST_AI_MODEL`.

Отдельного набора frontend unit- и end-to-end-тестов и настроенного CI-пайплайна в репозитории пока нет.

## Ограничения и развитие

Текущие технические ограничения:

- Интерфейс работает с одной автоматически выбранной семьёй.
- При старте загружаются данные сразу нескольких разделов. Бюджетная история ограничена 24 месяцами и 3000 операциями; чат — последними 100 сообщениями без подгрузки старых в интерфейсе.
- У некоторых быстрых действий есть оптимистическое обновление без отката при сетевой ошибке.
- Обновления чатов доставляются через WebSocket; остальные разделы не имеют общей синхронизации в реальном времени.
- WebSocket-hub и лимитеры хранят состояние в памяти процесса; несколько экземпляров API потребуют решения для общей доставки событий и лимитов.
- Сборка frontend содержит крупные JS-бандлы; разделение загрузки страниц остаётся задачей оптимизации.

Направления дальнейшей разработки, без закреплённых сроков:

1. Настоящее подтверждение телефона и переключение семей.
2. Серверные карта, геолокация, галерея, SOS и check-in.
3. Платёжный провайдер, подтверждение платежей и реальное продление подписки.
4. Загрузка позиций чеков и полноценный совместный список покупок.
5. Push-уведомления, напоминания, повторяющиеся события и расширенная аналитика.
6. OpenAPI-спецификация, frontend-тесты, автоматические проверки CI и оптимизация загрузки.

В репозитории есть скрипт публикации статической сборки на GitHub Pages (`frontend/deploy.mjs`). Для работы семейных данных нужен доступный `/api`; одна статическая публикация не разворачивает backend и базу.
