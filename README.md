# <img src="_docs/assets/famigo-logo.png" alt="Логотип Famigo" width="40" height="40" align="absmiddle"> Famigo

**Всё важное для семьи в одном месте.**

Документация сверена с текущим кодом **17 ноября 2026 года**.

Famigo — веб-приложение для совместной организации семейной жизни. Участники семьи ведут общий бюджет, планируют события, распределяют домашние дела, следят за продуктами и общаются в семейном и личных чатах.

Основная единица приложения — семейная группа. Она объединяет участников с разными правами, дома, продукты, финансовые операции, события и переписку. Часть данных связана с конкретным домом, остальные относятся ко всей семье.

Проект развивается как учебный fullstack-продукт. Основные сценарии работают через Go API и PostgreSQL. Для будущих возможностей подготовлены демонстрационные экраны; их статус описан отдельно.

## Возможности

### Реализовано с сохранением на сервере

| Раздел | Что доступно |
| --- | --- |
| Аккаунт | Регистрация после подтверждения почты, проверка сложности пароля, Yandex SmartCaptcha, вход с кодом на почту, сброс пароля, восстановление сессии, выход на одном или всех устройствах, смена пароля, удаление аккаунта с проверкой пароля |
| Профиль | Имя, дата рождения, телефон, аватар, пищевые предпочтения и ограничения без повторного чекбокса; условия включены в основное согласие |
| Семья | Создание группы, вступление по коду, приглашение по ссылке, просмотр участников, управление ролями |
| Дома | Создание и редактирование домов, назначение жильцов, домашние дела с отметками выполнения |
| Холодильник | Продукты каждого дома: категории, количество, единицы измерения и сроки годности; поиск и фильтрация в интерфейсе |
| Бюджет | Добавление доходов и расходов, привязка к дому, история операций, фильтры и сводные показатели |
| Календарь | Создание событий с выбранными участниками, просмотр по дням, неделям и месяцам, представление списком |
| Чаты | Общий семейный и личные чаты, WebSocket, ответы с переходом к исходному сообщению, пересылка, рецепты, фото и видео, просмотр изображений, профили по аватарке, счётчики непрочитанных, прочтение всеми получателями, закрепление и отключение уведомлений |
| Уведомления | Лента, счётчик непрочитанных, отметка одного или всех уведомлений прочитанными, настройки получения |


Раздел рецептов объединяет серверный AI-подбор по продуктам дома и личное избранное. Сгенерированный рецепт можно сохранить, удалить из избранного и отправить в доступный семейный или личный чат. Избранное сохраняется на сервере и доступно после повторного входа. Доступ к разделу в текущем интерфейсе предоставляется на Premium+.

Главная страница собирает сводку по бюджету, событиям, продуктам, домашним делам и чатам. Интерфейс поддерживает мобильные и настольные экраны.

## Пользовательский сценарий

1. Начать регистрацию: указать имя, почту, пароль и дату рождения, отдельно принять соглашение и согласие на обработку данных, пройти настроенную SmartCaptcha. До проверки кода данные находятся во временной заявке `pending_registrations`, аккаунта в `users` ещё нет.
2. Подтвердить почту шестизначным кодом из письма: пользователь, настройки, согласия и сессия создаются одной транзакцией. Код требуется также при входе с паролем.
3. Создать семью или присоединиться по приглашению. Аккаунту без семьи доступна главная страница; семейные разделы требуют вступления в группу.
4. Добавить дома, назначить жильцов и пригласить остальных участников.
5. Вести бюджет, календарь, продукты и домашние дела; обсуждать их в чатах.
6. При необходимости оформить демонстрационную подписку Premium+ и подобрать блюда по содержимому холодильника.

В семье есть три роли: **Owner**, **Admin** и **Member**. Владелец и администраторы управляют домами, участниками и подпиской в пределах своих полномочий. Права проверяются сервером; скрытие кнопки в интерфейсе не заменяет проверку доступа.

Когда владелец выходит из семьи или удаляет аккаунт, владельцем автоматически становится администратор с самой ранней датой назначения. Если администраторов нет, права получает участник, который раньше всех вступил в семью. Если участников больше нет, семья удаляется. Повторное назначение после снятия роли администратора начинает новый отсчёт. Для администраторов, назначенных до добавления учёта этой даты, используется дата вступления: история прежних назначений не сохранялась.

Сервер поддерживает членство в нескольких семьях. Текущий интерфейс загружает первую семью из списка; отдельного переключателя семей пока нет.

## Архитектура

```text
Браузер
  └─ nginx :8080
      ├─ /Famigo/ → React SPA
      └─ /api/    → Go API
                      ├─ PostgreSQL
                      ├─ файлы аватаров
                      ├─ Яндекс SMTP / Resend → письма с кодами
                      ├─ GigaChat → подбор рецептов
                      └─ Yandex SmartCaptcha → проверка токена капчи
```

Frontend обращается к API по относительному адресу `/api`. В разработке HTTP-запросы и WebSocket проксирует Vite, в Docker — nginx. Приложение использует базовый путь `/Famigo/`.

Браузер загружает виджет SmartCaptcha непосредственно с серверов Яндекса. Секретный
ключ остаётся в backend. Фото и видео чатов хранятся в PostgreSQL; пользовательские
аватары — в файловом хранилище backend, в Docker это отдельный том.

Серверные модули следуют схеме **handler → service → repository**: обработчик проверяет HTTP-запрос, сервис выполняет бизнес-правила, репозиторий работает с БД. Подключение модулей находится в `backend/internal/server/routes.go`.

`frontend/src/store/DataProvider.jsx` загружает профиль и семейные данные, предоставляет действия страницам и обрабатывает события чата. `frontend/src/api/mappers.js` преобразует серверные форматы в данные интерфейса.

## Запуск через Docker

Compose запускает frontend, backend и PostgreSQL. Рецепты генерируются внешним GigaChat API; локальная модель и GPU не нужны.


### Требования

- Docker с Compose 2.30 или новее.
- Яндекс Почта с разрешённым доступом почтовых клиентов и паролем приложения для отправки кодов.
- Свободное место для Docker-образов, базы и загружаемых медиа.

### Подготовка

При отдельной установке на другом компьютере создаются собственные локальная БД и секреты. Файл автора проекта копировать не нужно. Если вы просто пользуетесь общим развёрнутым сайтом, локальная установка и ключи не требуются.

1. Создайте в корне проекта файл `secrets.env`. Если он уже существует, используйте его, не создавая заново.
2. Убедитесь, что в корневом `.gitignore` есть строка `secrets.env`. В этом репозитории она уже добавлена: настоящий файл с паролями и ключами не должен попадать в Git.
3. Заполните `secrets.env` по [шаблону secrets.env.example](secrets.env.example), заменив все заполнители в угловых скобках своими значениями. Сам шаблон содержит только подсказки и хранится в Git. Пример структуры:

```dotenv
POSTGRES_PASSWORD='<пароль базы данных>'
DATABASE_URL='postgres://famigo:<URL-кодированный пароль>@localhost:15432/famigo?sslmode=disable'
DOCKER_DATABASE_URL='postgres://famigo:<URL-кодированный пароль>@db:5432/famigo?sslmode=disable'
JWT_SECRET='<случайный секрет длиной не менее 32 символов>'
MESSAGE_KEYS='1:<случайный ключ из 32 байт в base64>'
SMTP_PASSWORD='<пароль приложения Яндекс Почты>'
# Для AI-рецептов:
GIGACHAT_AUTH_KEY='<ключ авторизации вашего проекта GigaChat>'
# Для капчи при регистрации и после ошибки входа:
SMARTCAPTCHA_CLIENT_KEY='<ключ клиента Yandex SmartCaptcha>'
SMARTCAPTCHA_SERVER_KEY='<ключ сервера Yandex SmartCaptcha>'
```

| Настройка | Что заполнить на другом компьютере |
| --- | --- |
| `POSTGRES_PASSWORD` | Свой надёжный пароль новой локальной БД |
| `DATABASE_URL`, `DOCKER_DATABASE_URL` | Тот же пароль с URL-кодированием; пользователь и база остаются `famigo` |
| `JWT_SECRET` | Собственный случайный секрет минимум 32 символа |
| `MESSAGE_KEYS` | Собственный отдельный случайный ключ из 32 байт в Base64, с префиксом `1:` |
| `SMTP_PASSWORD` | Пароль приложения Яндекс Почты, созданный в настройках Яндекс ID |

В URL закодируйте специальные символы пароля, например `@` → `%40`, `#` → `%23`, `$` → `%24`, `%` → `%25`; `POSTGRES_PASSWORD` оставьте исходным. Для существующей БД изменения файла недостаточно: см. [смену пароля](#подключение-к-бд-через-pgadmin).

Для генерации JWT-секрета и ключа сообщений можно использовать PowerShell:

```powershell
function New-FamigoKey {
    $bytes = New-Object byte[] 32
    $generator = [System.Security.Cryptography.RandomNumberGenerator]::Create()
    try { $generator.GetBytes($bytes) } finally { $generator.Dispose() }
    [Convert]::ToBase64String($bytes)
}
New-FamigoKey # первое значение — JWT_SECRET
New-FamigoKey # второе значение — MESSAGE_KEYS, добавьте перед ним 1:
```

Не публикуйте полученные значения. В качестве альтернативы при установленном OpenSSL выполните `openssl rand -base64 32` отдельно для каждого ключа. Сохраняйте ключ сообщений для своей БД: его потеря делает зашифрованные сообщения нечитаемыми.

4. Настройте почту. В `.env` и `backend/.env` сейчас указан отправитель `famigonoreply@yandex.ru`. Для собственного ящика Яндекса замените `SMTP_USERNAME` и `EMAIL_FROM` в корневом `.env`, а для запуска Go вне Docker — также в `backend/.env`; в `SMTP_PASSWORD` укажите пароль приложения именно этого аккаунта. При общем тестовом почтовом аккаунте команда передаёт только его пароль приложения отдельно, например через менеджер паролей. Обычный пароль Яндекс ID не подходит. Без настроенной отправки писем регистрация и вход через код недоступны.

Resend и `RESEND_API_KEY` нужны только при выборе `EMAIL_PROVIDER=resend`. Для локальной Ollama внешний AI-ключ не требуется. Шаблон находится в Git; заполненный `secrets.env` исключён через `.gitignore`.

Для собственной копии проекта используйте свою почту: измените `SMTP_USERNAME` и
`EMAIL_FROM` в используемом `.env` и задайте пароль приложения этого аккаунта.
Коллегам не нужно передавать ваши ключи. Для SmartCaptcha создайте собственную
капчу и добавьте хосты `localhost` и `127.0.0.1`; ключи и сценарии описаны ниже.
Если оба ключа капчи отсутствуют, интеграция выключена; если задан только один,
backend сообщает об ошибке конфигурации. При `AI_PROVIDER=gigachat` ключ GigaChat
обязателен уже для запуска backend. Чтобы запустить свою копию без AI, задайте
`AI_PROVIDER=openai` и пустой `AI_BASE_URL` в используемом `.env`.

### Запуск

Из корня репозитория:

```bash
docker compose --env-file .env --env-file secrets.env up -d --build
```

Откройте [http://localhost:8080/Famigo/](http://localhost:8080/Famigo/). Проверка API: [http://localhost:8080/api/health](http://localhost:8080/api/health).

Таблицы создаются автоматически при запуске backend. AI-подбор обращается к GigaChat через интернет; модель на компьютер не скачивается.

```bash
# Состояние сервисов и сообщения backend
docker compose ps
docker compose logs --tail=100 backend

# Остановка с сохранением данных
docker compose down
```


Без `SMTP_PASSWORD` сервер запускается с предупреждением, а регистрация и вход отвечают `503 email_unavailable`. Настройка Яндекс SMTP описана в [документации backend](backend/README.md#яндекс-smtp).

## Локальная разработка

### Backend

Нужны Go в соответствии с `backend/go.mod` (сейчас `go 1.27.1`, toolchain `go1.27.3`) и PostgreSQL. В Docker используется PostgreSQL 17.

Добавьте в корневой `secrets.env` строку подключения к своей локальной базе:

```dotenv
DATABASE_URL=postgres://famigo:<URL-кодированный пароль>@localhost:15432/famigo?sslmode=disable
```

Пример использует базу из текущего Compose. Для отдельного PostgreSQL укажите его фактический порт, обычно `5432`. Не запускайте Docker-frontend одновременно с локальным Go-сервером на порту `8080`: сначала остановите `frontend` и `backend`, оставив `db`. Для специальных символов в пароле используйте URL-кодирование. База и пользователь должны существовать до запуска; таблицы создадут миграции. Для входа также нужны почтовые настройки из раздела выше.

```bash
cd backend
go run ./cmd/api
```

Сервер читает `backend/.env` и ищет `secrets.env` в текущей папке и на уровень выше. API по умолчанию слушает `http://localhost:8080`.

При локальном запуске Go приоритет такой: окружение процесса → `.env` → `secrets.env`. Путь к внешнему файлу секретов можно указать через `SECRETS_FILE`.

Compose получает значения подстановок из `--env-file` и окружения, затем передаёт настройки контейнерам. При изменении настроек используйте ту же команду запуска с обоими `--env-file`. В контейнере используется `DOCKER_DATABASE_URL`, если задан; иначе `DATABASE_URL` строится из `POSTGRES_PASSWORD`. Отдельная локальная строка `DATABASE_URL` его не заменяет. Для паролей со спецсимволами задайте URL-кодированный пароль в обеих строках подключения: `DOCKER_DATABASE_URL` с адресом `db:5432`, `DATABASE_URL` с адресом `localhost:15432`. ## Подключение к БД через pgAdmin

Для pgAdmin на компьютере используйте: сервер `127.0.0.1`, порт `15432`, база `famigo`, пользователь `famigo`. Пароль — исходное значение `POSTGRES_PASSWORD` без окружающих кавычек, а не URL-кодированная строка. В Docker используется адрес `db:5432`. Порт опубликован только на loopback; используйте актуальный Docker Engine (28.0.0 или новее для исправления прежних ограничений loopback-публикации).

В pgAdmin: **Register → Server → Connection**. Таблицы: **Databases → famigo → Schemas → public → Tables**; просмотр: **View/Edit Data**. Пользователь `famigo` имеет широкие права — изменения из pgAdmin затрагивают реальные данные приложения.

При смене пароля существующей БД:

1. Измените пароль роли `famigo` через **Login/Group Roles → famigo → Properties → Definition → Password** и сохраните.
2. Обновите `POSTGRES_PASSWORD`, `DATABASE_URL` и `DOCKER_DATABASE_URL` в `secrets.env`. В двух URL пароль должен быть URL-кодирован, в первом значении — исходный. Одинарные кавычки предотвращают подстановки символа доллара в Compose.
3. Выполните `docker compose --env-file .env --env-file secrets.env up -d db backend` и обновите сохранённый пароль pgAdmin.

Пересоздание контейнера сохраняет том, но не меняет пароль в уже инициализированном PostgreSQL. Не удаляйте том ради смены пароля. Внутренняя проверка `psql` через Unix-сокет может работать с `trust` и не доказывает правильность пароля для сетевого подключения.

## Подбор рецептов

На тарифе Premium+ пользователь выбирает дом, число порций, категорию блюда и участников, чьи ограничения нужно учитывать. Сервер получает пригодные продукты холодильника и формирует подборку из пяти разных рецептов.

Генерация включает выбор идей, подробное описание приготовления и дополнительную сверку ингредиентов со всеми шагами. В ответе отмечается, какие продукты есть дома и что нужно докупить. Сервер проверяет ограничения и повторы; если полноценную подборку получить не удалось, возвращается ошибка.

Сейчас в `.env` и `backend/.env` выбран `AI_PROVIDER=gigachat`, модель `GigaChat-2-Pro`, режим `GIGACHAT_API_PERS`. Ключ `GIGACHAT_AUTH_KEY` хранится только в `secrets.env`. OAuth-токен кешируется в памяти, обновляется заранее и один раз после 401; запросы выполняются последовательно. Формат строгой JSON-схемы адаптирован под GigaChat. Проверка TLS включена; официальные сертификаты НУЦ встроены только в AI-клиент.


Генерация может занимать несколько минут. Ответы модели дополнительно проверяются приложением, однако пользователю всё равно следует проверять состав и инструкции, особенно при аллергиях. Имена и почта участников не включаются в запрос; модели передаются продукты, ограничения и текстовые пожелания к питанию.

Пока запрос выполняется, выбор дома, участников, порций и категории заблокирован.
Результат можно сохранить в личное избранное и отправить в доступный чат. Название,
ингредиенты и шаги сохранённого рецепта остаются на языке генерации; подписи кнопок,
порций, времени и распознанных единиц измерения отображаются на языке интерфейса.
API избранного `/api/me/recipes` проверяет авторизацию и принадлежность записи
пользователю; проверка Premium+ на сервере применяется к генерации. В интерфейсе
весь раздел рецептов открывается на Premium+.

## Вход, регистрация и капча

При регистрации пароль должен содержать не менее восьми символов, латинскую букву
`A–Z` или `a–z`, цифру `0–9` и специальный символ, например `! @ # $ % & *`.
Верхняя граница — 72 байта. Форма во время ввода показывает только недостающие
требования; когда они выполнены, подсказка исчезает. У каждого поля пароля есть
кнопка просмотра/скрытия. Проверка регистрации также выполняется на сервере.

При настроенных ключах SmartCaptcha:

- На регистрации капча показана сразу; без прохождения продолжить нельзя.
- Первая попытка входа проходит без капчи. После неверной почты или пароля капча
  появляется, кнопка входа блокируется до её прохождения.
- Backend проверяет одноразовый токен Яндекса и разрешённый хост. После следующей
  ошибки нужен новый токен; сбой проверки не разрешает вход в обход капчи.
- Требование для входа хранится в PostgreSQL по HMAC IP-адреса. Перезагрузка,
  очистка cookies и смена почты его не снимают; пользователи за одним внешним IP
  разделяют это требование. После успешной проверки данных входа оно снимается.

При регистрации до проверки кода существуют только временные данные в
`pending_registrations`. После подтверждения создаются пользователь, настройки,
согласия и сессия. При входе после правильного пароля по-прежнему требуется код
из письма. При сбросе пароля новый пароль сохраняется после проверки кода,
старые сессии завершаются, пользователь входит заново.

Виджет использует светлую/тёмную тему. Подсказки приложения доступны на шести языках;
для виджета Яндекса используются русский и английский. В списке сайтов капчи
указываются хосты без схемы, порта и пути. В ответе проверки Яндекс может вернуть
хост с портом, например `localhost:8080`; backend сравнивает извлечённое имя хоста.
Настройка: [Yandex SmartCaptcha в backend](backend/README.md#yandex-smartcaptcha).

Вкладки одного профиля браузера используют общую refresh-cookie. Для одновременного
тестирования разных учётных записей используйте разные профили браузера, другой
браузер либо обычное окно и инкогнито.

## Медиа и пересылка в чатах

Слева от поля сообщения находится скрепка. Её меню позволяет выбрать фото/видео из
файлов или галереи, снять фото либо видео на поддерживаемом устройстве. Отдельных
постоянных кнопок съёмки нет. Работа камеры и доступ к галерее зависят от браузера,
устройства и его разрешений.

Один файл — до **25 МиБ**; поддерживаются JPEG, PNG, GIF, WebP, MP4, WebM и MOV.
HEIC преобразуется в JPEG на клиенте. Воспроизведение видео зависит от кодеков
браузера. Общая тарифная квота хранения медиа чатов сейчас не проверяется.
Локальная галерея приложения — отдельный демонстрационный раздел.

При клике на фотографию открывается просмотрщик; имя файла показывается только
в нём. Закрыть его можно крестиком, Escape или кликом мимо изображения. Видео
воспроизводится внутри сообщения. Рецепт в чате показывает состав и раскрываемое
приготовление, без кнопок сохранения и отправки.

«Ответить» и «Переслать» доступны в контекстном меню по правой кнопке мыши;
на сенсорном устройстве — по долгому нажатию, с клавиатуры — Shift+F10.
Клик по цитате прокручивает к исходному сообщению и ненадолго подсвечивает его.
Если нужного сообщения нет в последних 100, история догружается по страницам.
У каждого входящего сообщения есть аватарка отправителя. Она открывает профиль;
возврат использует историю переходов и сохранённую позицию чата.

**Одна галочка — «Доставлено»**, когда сообщение сохранено сервером.
**Две галочки — «Прочитано»**, когда его увидели все текущие участники, кроме автора.
Экран отправляет отдельные просмотры только для сообщений в видимой области
активной вкладки. Простое открытие чата, отправка ответа и просмотр более позднего
сообщения не отмечают пропущенную историю прочитанной. Скрытая вкладка и открытый
просмотрщик медиа не отправляют новые отметки; статусы сохраняются в PostgreSQL.
Если пользователь читает историю, новое сообщение не принуждает прокрутку вниз.

Вложения сохраняются в PostgreSQL, требуют авторизации и членства в целевом чате.
При пересылке сервер проверяет доступ к исходному и целевому чатам и создаёт
отдельную копию файла. Удаление оригинала не удаляет уже пересланную копию.
При заданном MESSAGE_KEYS шифруются текст, содержимое рецептов и цитат, файлы, их названия и MIME-типы. Это защита хранения, не сквозное шифрование.
Подписи действий, просмотра, порций, времени, единиц и статусов переводятся на язык
интерфейса; текст сообщения и рецепта автоматически не переводится.

## Алкоголь и возраст

Категория «Алкоголь» доступна в холодильнике и подборе рецептов при серверном признаке `canUseAlcohol` из `/api/me`. Он рассчитывается по дате рождения в БД; отсутствие даты закрывает доступ. Граница — 18-летие по московскому времени. Несовершеннолетним API не возвращает алкогольные продукты, запрещает их добавление/изменение и алкогольную генерацию; известные названия спиртного распознаются и при попытке указать другую категорию. Для генерации алкоголя также требуется совершеннолетие всех выбранных едоков.

В остальных запросах несовершеннолетних спиртное исключается из продуктов и добавляется обязательное ограничение «Без алкоголя». Ответ модели проверяется сервером по названиям и инструкциям, нарушения отбрасываются. Это программная фильтрация известных терминов, а не лабораторная проверка состава. Возраст берётся из указанной в профиле даты рождения: проверка документов и достоверности даты не реализована.

## Тарифы

В Famigo три тарифа: **Free**, **Premium** и **Premium+**. Подписка оформляется на семейную группу: её возможности получают все участники этой семьи. Отдельная подписка для каждого пользователя не требуется. Для другой семейной группы тариф определяется независимо.

Оформлять подписку, менять тариф и управлять настройкой продления могут только
**Owner** и **Admin**. **Member** видит цены, текущий тариф и пользуется его
возможностями, но кнопки покупки и управления ему не показываются. Backend
проверяет роль для каждого изменения; прежняя оплата не сохраняет права после
понижения роли. Поле плательщика фиксирует автора оформления, а не владельца прав.

плата за семейную группу, без доплаты за каждого участника. Год равен десяти
месяцам — **4 990/14 990 ₽**, экономия около 16,7%. Это проектное ценообразование,

### Free — базовое семейное пространство

Бесплатный тариф действует по умолчанию, если у семьи нет активной платной подписки. Он позволяет пользоваться основными разделами: участниками, домами, домашними делами, холодильником, бюджетом, календарём, чатами и уведомлениями.

Семья может создать до двух домов. Например, квартиру и дачу: у каждого дома будет собственный набор продуктов и дел. При попытке добавить третий дом сервер вернёт ошибку ограничения тарифа.

На Free недоступны раздел рецептов, геолокация, история мест, check-in и QR-сканер чеков. При этом расходы можно добавлять вручную, а продукты — учитывать без подбора блюд.

### Premium — дополнительный дом и демонстрационные функции заботы

Premium стоит **499 ₽ за месяц** или **4 990 ₽ за год**. Годовая стоимость на 998 ₽ ниже двенадцати месячных периодов — экономия около 16,7%, в интерфейсе округляется до 17%. Средняя стоимость при годовом периоде — 415,83 ₽ в месяц.

Тариф включает базовые функции Free и увеличивает лимит до трёх домов. В интерфейсе также открываются геолокация, сохранённые места, история мест за семь дней и «Я в порядке»; лимит локальной галереи увеличивается до 10 ГиБ.

Главное реализованное серверное отличие от Free — возможность создать третий дом. Геолокация и функции заботы пока демонстрационные. Раздел рецептов и QR-сканер на Premium остаются закрыты.

### Premium+ — рецепты и расширенные лимиты

Premium+ стоит **1 499 ₽ за месяц** или **14 990 ₽ за год**. Годовой период на 2 998 ₽ дешевле двенадцати месячных — экономия около 16,7%. Средняя стоимость — примерно 1 249,17 ₽ в месяц.

Тариф включает возможности Premium и добавляет:

- Создание домов без числового ограничения со стороны тарифа.
- Избранные рецепты и AI-подбор пяти блюд из продуктов выбранного дома.
- Учёт пищевых ограничений всей семьи или выбранных участников при подборе.
- Выбор категории блюда и числа порций, подробные инструкции и список недостающих ингредиентов.
- QR-сканер для заполнения суммы и даты расхода.
- Историю демонстрационных мест за 30 дней и лимит локальной галереи 100 ГиБ.

Для AI-подбора дополнительно нужна настроенная и доступная модель на сервере. Подписка не отменяет ограничения частоты запросов, очередь к модели и общий таймаут генерации.

### Оформление и управление

Тариф выбирается на странице `/premium`: пользователь переключает месячный или годовой период и подтверждает оформление в диалоге без повторного чекбокса соглашения. В текущем режиме банковские данные не запрашиваются, деньги не списываются.

| Действие | Кто может выполнить |
| --- | --- |
| Оформить или сменить платный тариф | Владелец или администратор семьи |
| Отключить или включить настройку продления | Только владелец или администратор семьи |
| Пользоваться доступными возможностями | Все участники семьи в пределах своих обычных прав |

Подписка расширяет доступные функции, но не повышает роль участника: например, Member не получает права создавать дома только благодаря Premium+.

При оформлении сервер сохраняет тариф, период, пользователя-плательщика и дату окончания: через один календарный месяц или год от момента запроса. Повторное оформление или смена тарифа заменяет текущую подписку и отсчитывает срок заново от этого момента. Перерасчёт остатка периода, доплаты и возвраты не реализованы.

### Продление, окончание срока и возврат на Free

Отключение продления сохраняет текущий тариф до конца установленного срока. Его можно снова включить до истечения подписки. Сейчас это изменение настройки в базе: механизма автоматической оплаты и продления срока нет. Даже при включённом продлении после окончания срока действующим тарифом становится Free, если подписка не оформлена заново.

При истечении подписки вся семья переходит на Free. Доступны только первые два добавленных дома; при Premium — первые три, при Premium+ — все. Порядок определяется датой создания, при совпадении — ID. Остальные дома видны в списке с пометкой о недоступности, но открыть, изменить или удалить их, работать с их делами, холодильником и генерацией рецептов нельзя, в том числе прямым запросом API. Дома и данные не удаляются; повышение тарифа восстанавливает доступ. Добавлять дома сверх текущего лимита нельзя. Интерфейс обновляет семейную подписку каждые 30 секунд и при возвращении в окно; сервер проверяет срок при каждом запросе.

Сервер пересчитывает активный тариф при обращении к подписке и защищённым тарифным операциям. Интерфейс получает подписку при загрузке семейных данных и её изменении; отдельного таймера обновления тарифа в открытой вкладке нет.

### Что проверяется сервером

Лимит создания домов и право пользоваться AI-рецептами проверяются на backend. Создание домов выполняется с блокировкой семьи, чтобы параллельные запросы не обходили ограничение. Тарифные ограничения демонстрационной карты, check-in, сканера и локальной галереи применяются интерфейсом; серверных API этих разделов пока нет.

Оформление работает только при `DEMO_PAYMENTS=true`. При выключенном режиме API возвращает `501 payments_unavailable`: настоящая покупка пока недоступна. Для production демо-оформление нужно отключить явно в конфигурации Compose.

## API и модель данных

API использует префикс `/api`, JSON и `Authorization: Bearer <accessToken>` для защищённых запросов. Обновление сессии выполняется через HttpOnly cookie. Денежные суммы на сервере хранятся целым числом копеек; даты передаются как `YYYY-MM-DD`, дата и время — RFC 3339.

| Группа | Назначение |
| --- | --- |
| `/api/health` | Готовность API и подключение к БД |
| `/api/auth/*` | Регистрация, вход, коды почты, обновление и завершение сессий |
| `/api/me` и вложенные адреса | Профиль, аватар, пароль, питание, настройки |
| `/api/families` | Список семей, создание и присоединение |
| `/api/families/:familyID/*` | Участники, дома, продукты, бюджет, календарь, чаты, подписка и рецепты |
| `/api/notifications` и вложенные адреса | Лента и отметки прочтения |
| `/api/chats/ws-ticket`, `/api/chats/ws` | Одноразовый билет и WebSocket |

Успешные запросы регистрации и входа возвращают запрос подтверждения (`challengeId`); токены выдаются после `POST /api/auth/email/verify`. WebSocket открывается с одноразовым билетом на 30 секунд. При обрыве frontend переподключается и обновляет данные чата.

Основные группы таблиц:

- Пользователи, регистрации и защита входа: `users`, `pending_registrations`, `user_settings`, `user_food_prefs`, `consents`, `verification_codes`, `refresh_tokens`, `login_captcha_gates`.
- Семья и быт: `families`, `family_members`, `family_invites`, `homes`, `home_tasks`, `products`.
- Финансы и планы: `transactions`, `events`, `event_members`, `subscriptions`.
- Общение: `chats`, `chat_members`, `messages`, `chat_media`, `message_views`, `notifications`; личное избранное — `recipe_favorites`.

SQL-миграции вшиваются в Go-приложение и выполняются при запуске под блокировкой PostgreSQL. Таблицы приложения создаются SQL, а не GORM AutoMigrate. Миграции геолокации, безопасности и галереи пока пустые. `backend/api/openapi.yaml` также является пустой заготовкой: готовой Swagger/OpenAPI-спецификации сейчас нет.

## Безопасность

- Пароли хешируются bcrypt; коды подтверждения действуют 10 минут, допускают пять неверных попыток, в базе хранится HMAC кода. На вход действуют лимиты по IP и почте; отдельной блокировки аккаунта на 15 минут после пяти неверных паролей сейчас нет.
- При настроенной SmartCaptcha регистрация и повторные попытки после неверного входа проверяются сервером. Капча дополняет ограничения частоты; секретный ключ не передаётся браузеру.
- Сброс пароля проверяет наличие аккаунта до формы кода и возвращает `422 account_not_found` для неизвестного адреса. Для существующего адреса отправка асинхронная: `202` не гарантирует доставку. После сброса прежние сессии завершаются; автоматического входа нет.
- Access-токен хранится в памяти frontend, refresh-токен — в HttpOnly cookie, в БД — его хеш. Refresh-токены ротируются; сервер проверяет актуальность сессии.
- Для семейных запросов проверяются членство и права. Изменения ролей и ряд операций с лимитами выполняются в транзакциях с блокировками.
- Используются параметризованные запросы, отдельные структуры входных данных и отклонение неизвестных JSON-полей.
- Настроены ограничения частоты и размера запросов, проверка Origin, защитные HTTP-заголовки и CSP.
- Аватары проверяются и перекодируются в JPEG перед сохранением.
- При заданном `MESSAGE_KEYS` AES-256-GCM защищает текст и детали сообщений (рецепты, цитаты, сведения о вложении), а также байты файлов, их названия и MIME-типы в `chat_media`. Сервер расшифровывает содержимое после проверки доступа к чату; это шифрование хранения, не сквозное. Старые данные переводятся на активный ключ до приёма запросов; при ошибке перевода сервер не запускается. Идентификаторы, авторство, время, членство и отметки прочтения остаются открытыми. Личное избранное вне чатов этим механизмом не защищается. В production ключ обязателен; сохраняйте его отдельно от базы, включая старые ключи, необходимые резервным копиям.
- В Docker backend и nginx работают без root. PostgreSQL опубликован только на `127.0.0.1:15432` для локального pgAdmin; внутри Docker используется `db:5432`.

Подробности реализации и ротации ключей описаны в [документации backend](backend/README.md).

## Проверки

Frontend:

```bash
cd frontend
npm run lint
npm run build
```

Backend:

```bash
cd backend
go test ./...
```

Go-тесты охватывают авторизацию, сложность паролей, SmartCaptcha, валидацию, middleware, шифрование, обработку аватаров, роли, тарифы, бюджет и AI-рецепты. Некоторые тесты используют временные локальные HTTP-серверы.

Интеграционный тест требует отдельной пустой PostgreSQL-базы и переменной `FAMIGO_TEST_DATABASE_URL`. Пример для PowerShell из папки `backend`:

```powershell
$env:FAMIGO_TEST_DATABASE_URL = 'postgres://famigo:<пароль>@localhost:15432/famigo_test?sslmode=disable'
go test ./internal/server ./internal/auth -v
Remove-Item Env:FAMIGO_TEST_DATABASE_URL
```

Тест применяет миграции и изменяет данные: используйте только выделенную тестовую базу. Без переменной этот сценарий пропускается. Необязательные проверки настоящей AI-модели запускаются с `FAMIGO_TEST_AI_URL` и, при необходимости, `FAMIGO_TEST_AI_MODEL`.

Отдельного набора frontend unit- и end-to-end-тестов и настроенного CI-пайплайна в репозитории пока нет.

## Ограничения и развитие

Текущие технические ограничения:

- Интерфейс работает с одной автоматически выбранной семьёй.
- При старте загружаются данные сразу нескольких разделов. Бюджетная история ограничена 24 месяцами и 3000 операциями. Чат сначала загружает 100 последних сообщений; старые догружаются при переходе по цитате, общей прокрутки всей истории с пагинацией пока нет.
- У некоторых быстрых действий есть оптимистическое обновление без отката при сетевой ошибке.
- Обновления чатов доставляются через WebSocket; остальные разделы не имеют общей синхронизации в реальном времени.
- WebSocket-hub и лимитеры хранят состояние в памяти процесса; несколько экземпляров API потребуют решения для общей доставки событий и лимитов.
- Состояние требования капчи хранится в БД, но само по себе это не обеспечивает распределённую доставку WebSocket или общие лимиты между процессами.
- Изменение фото семьи пока является заглушкой; кнопка видна только Owner/Admin. Серверной загрузки аватарки семьи нет.
- Сборка frontend содержит крупные JS-бандлы; разделение загрузки страниц остаётся задачей оптимизации.

Направления дальнейшей разработки, без закреплённых сроков:

1. Настоящее подтверждение телефона и переключение семей.
2. Серверные карта, геолокация, галерея, SOS и check-in.
3. Платёжный провайдер, подтверждение платежей и реальное продление подписки.
4. Загрузка позиций чеков и полноценный совместный список покупок.
5. Push-уведомления, напоминания, повторяющиеся события и расширенная аналитика.
6. OpenAPI-спецификация, frontend-тесты, автоматические проверки CI и оптимизация загрузки.

В репозитории есть скрипт публикации статической сборки на GitHub Pages (`frontend/deploy.mjs`). Для работы семейных данных нужен доступный `/api`; одна статическая публикация не разворачивает backend и базу.
